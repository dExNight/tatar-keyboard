# Функциональность: MVP, автокоррекция и татарские словари

Дата ресерча: 2026-07-18. Контекст: нативная Android-клавиатура (IME) с татарской кириллической раскладкой (ә ө ү җ ң һ), стиль iOS, приоритет — слабые/бюджетные устройства, разработчик-новичок.

---

## 1. Scope MVP

Принцип: MVP — это клавиатура, которой реально можно пользоваться каждый день вместо Gboard, без «умных» функций. Предикшен — самая дорогая часть, её выносим в v1.

### MVP (обязательно)

| Фича | Что именно | Замечания по реализации |
|---|---|---|
| Раскладка тат. кириллица | Русская ЙЦУКЕН (11/11/9 клавиш) + **дополнительный пятый ряд из 6 отдельных клавиш `ә ө ү җ ң һ`** над буквенной сеткой; long-press на базовых буквах (а→ә, о→ө, у→ү, н→ң, ж→җ, х→һ, э→ә, г→һ) дублирует доп. буквы как второй путь ввода | **Единое решение проекта** (согласовано с 05 §3–4.5: ә = 6.65%, 5-я буква языка — long-press как единственный механизм неприемлем). Доп. ряд ниже основных клавиш (~0.75–0.8 высоты буквенного ряда), 6 широких клавиш не ломают iOS-эстетику. Компактный вариант «без доп. ряда, только long-press» — опция в настройках, не дефолт. Детали сетки и проверка геометрии — см. «Дополнение» ниже |
| Русская раскладка + латиница (QWERTY) | Переключение по глобусу | Без русской раскладки клавиатурой никто не будет пользоваться — татарский пользователь двуязычен |
| Shift / Caps Lock | Один тап = следующая буква заглавная, двойной тап = caps lock, автокапитализация после `. ! ?` и в начале поля | Автокапитализация читается из `EditorInfo.inputType` (`TYPE_TEXT_FLAG_CAP_SENTENCES`) |
| Цифры/символы | Слой `?123` + второй слой `#+=` как в iOS. Long-press на верхнем ряду букв = цифры (опционально) | Просто другая KeyboardLayout, ничего сложного |
| Попапы (key preview) | Увеличенная буква над клавишей при нажатии + попап выбора при long-press | Рисовать самим в отдельном окне (`PopupWindow`) или внутри вью клавиатуры; системный `KeyboardView` deprecated с API 29 — рисуем свой View |
| Backspace | Одиночное удаление + автоповтор при удержании (начальная задержка ~400 мс, повтор ~50 мс, ускорение) | `Handler.postDelayed` / корутина; удалять через `InputConnection.deleteSurroundingText(1,0)` с учётом суррогатных пар (эмодзи!) — правильно `getTextBeforeCursor` и удаление целого кодпоинта/grapheme cluster |
| Пробел / Enter | Enter меняет вид/действие по `EditorInfo.imeOptions` (Search/Send/Go/Done/Next). Пробел: двойной тап = «. » (настройка) | `sendKeyEvent` или `performEditorAction` |
| Переключение языков | Кнопка-глобус: цикл тат→рус→en; long-press = меню выбора; уважать `Subtype` API (`InputMethodSubtype`), чтобы система показывала язык | Subtypes объявляются в `res/xml/method.xml` |
| Вибро/звук отклика | `performHapticFeedback(KEYBOARD_TAP)` | Дёшево, сильно влияет на ощущение качества |
| Курсор-навигация по свайпу пробела | Свайп по пробелу двигает курсор (фирменная фича iOS) | ~50 строк кода, дёшево, «вау-эффект» |

### Отложить из MVP (v1)

- Автокоррекция + строка подсказок (suggestion strip) — см. разделы 2–4.
- Пользовательский словарь (заученные слова).
- Эмодзи-панель.
- Настройки: высота клавиатуры, темы (light/dark по `uiMode` — в MVP только авто).

### Отложить надолго («потом»)

- Свайп-ввод (glide typing), голосовой ввод, история буфера, стикеры/GIF, однорукий режим, next-word prediction по биграммам, инкогнито-режим.

## 2. Как устроен предикшен в AOSP LatinIME / HeliBoard

### Архитектура

AOSP LatinIME (`packages/inputmethods/LatinIME` в AOSP; актуальный живой форк — **HeliBoard**, GitHub Helium314/HeliBoard, GPL-3.0) состоит из:

- **Java/Kotlin-слой**: `LatinIME extends InputMethodService`, `Suggest`, `DictionaryFacilitator` (объединяет main/user/history-словари), `WordComposer` (текущее набираемое слово + координаты касаний).
- **Нативный C++ движок** (`native/jni`, библиотека `libjni_latinime.so`): класс `BinaryDictionary` (Java) через JNI зовёт C++ код, который делает поиск по словарю с учётом опечаток.
- **Формат словаря `.dict`**: сериализованный **trie (patricia trie)** с частотами (1 байт, 0–255), флагами и биграммами. Форматы version 2 (статичный, mmap-only) и version 4 (updatable — для user-history). Main-словари — v2.
- **Поиск с исправлением**: обход trie с допущением edit-операций (замена/вставка/пропуск/транспозиция) + **пространственная модель** — учитываются координаты касания и близость клавиш (`ProximityInfo`: для каждой клавиши список соседей). Скор = вес ошибок × частота слова × бонусы (совпадение первой буквы и т.п.). Это по сути beam search по trie, без ML.
- Биграммы в словаре дают **next-word prediction** (подсказка следующего слова после пробела).

Важно для слабых устройств: `.dict` файл **mmap-ится**, а не загружается в кучу — RAM-след словаря минимален (страницы подгружаются по мере обхода trie). Словарь на 100–200 тыс. слов весит порядка **1–4 МБ** на диске (main_en в AOSP ~1–2 МБ); это и есть порядок «стоимости».

### Варианты для проекта (по возрастанию сложности)

1. **Форкнуть HeliBoard целиком**, заменить UI-слой на свой iOS-стиль, добавить раскладку tt и словарь. Плюс: предикшен, попапы, subtypes — всё готово. Минус: большая незнакомая кодовая база (но именно так HeliBoard вырос из OpenBoard, а OpenBoard из AOSP). Лицензия GPL-3.0 → ваш форк тоже GPL.
2. **Писать своё IME с нуля, а движок предикшена взять из LatinIME**: выдрать `native/jni` + Java-обёртку `BinaryDictionary` довольно трудоёмко (много связей). Реалистичнее — в v1 написать **свой простой предикшен**: словарь как отсортированный массив/DAWG в памяти или SQLite/бинарный файл, top-N по префиксу + расстояние Дамерау–Левенштейна ≤2 по кандидатам с учётом соседних клавиш. Для словаря в 100–200 тыс. слов на кириллице это укладывается в единицы мегабайт и <5 мс на запрос даже на бюджетном SoC — проверено практикой аналогичных клавиатур.
3. Гибрид: своё IME, а словарь компилировать в AOSP-формат `.dict` и подключить упрощённый порт нативного движка. Самый дорогой путь для новичка — не рекомендуется.

**Рекомендация**: итоговое решение по базе проекта сведено в **06-fork-ili-s-nulya.md, раздел «Дополнение: сведение решения по базе проекта»** — это единственный источник правды. Коротко: по умолчанию форк Simple Keyboard + путь 2 (свой простой предикшен в v1); путь 1 (форк HeliBoard) — если AOSP-предикшен нужен с первой версии и GPL приемлема; путь 3 подтверждён как «не делаем» (оценка «самый дорогой» верифицирована в 06: движок = ~300 файлов C++ + 40+ Java-классов пайплайна, прецедентов чистого выдирания нет).

### Как собрать словарь для нового языка (AOSP/HeliBoard-формат)

Формат исходника — текстовый `wordlist.combined`:

```
dictionary=main:tt,locale=tt,description=Tatar,date=1752800000,version=54
 word=һәм,f=255
 word=белән,f=252
 word=мин,f=250,flags=hand-added
  bigram=сине,f=2
```

- `f` — «логарифмическая» частота **0–255** (не сырые счётчики! частая ошибка), 255 = самые частые слова.
- Флаги: `possibly_offensive=true`, `abbreviation`, `nonword` и др.
- Биграммы — вложенные строки `bigram=` под словом.
- Слово ≤ ~48 символов.
- `version>18` нужен для совместимости со старым AOSP-кибордом (для HeliBoard не обязателен).

Компиляция:

```bash
java -jar dicttool_aosp.jar makedict -s tt_wordlist.combined -d main_tt.dict
```

`dicttool_aosp.jar` — из репозитория remi0s/aosp-dictionary-tools (собран из AOSP `tools/dicttool`). В репозитории Helium314/aosp-dictionaries (Codeberg) — готовые словари, описание формата и экспериментальные python-скрипты создания wordlist из корпуса предложений (медленные, требуют hunspell-словарь для фильтрации мусора). **Татарского словаря в списке aosp-dictionaries по состоянию на поиск не видно** — его придётся собрать самому (и потом можно законтрибьютить через discussion в HeliBoard — хороший способ проверить качество).

Пайплайн сборки татарского wordlist (реалистичный план):
1. Взять корпус предложений (см. раздел 3), почистить (убрать латиницу, цифры, ники).
2. Посчитать частоты токенов; отфильтровать через морфоанализатор apertium-tat (аналог hunspell-фильтра: слово валидно, если анализатор его разбирает) — отсекает опечатки корпуса.
3. Отобрать top 100–250 тыс. форм (татарский агглютинативный — словоформ много, лемм мало; в словарь кладут именно **словоформы**, trie хорошо сжимает общие префиксы).
4. Нормировать частоты в 0–255 логарифмически: `f = min(255, round(255 * log(c+1)/log(c_max+1)))`.
5. Скомпилировать, проверить в HeliBoard (словарь подключается как файл: Languages & layouts → «+» у Dictionaries).

Важно про агглютинативность: словарь словоформ покрывает меньше, чем у английского (в apertium-экосистеме татарский трансдьюсер даёт ~91% покрытия корпуса при 55K основ — а сырой частотный словарь форм даст меньше). Для MVP/v1 это нормально: 150–250 тыс. частотных форм закрывают подавляющую часть бытовой переписки. Морфологический предикшен (генерация форм на лету) — исследовательская задача, «потом».

## 4. Оценка «тяжёлых» фич для слабых устройств

| Фича | Сложность разработки | Стоимость на слабом устройстве | Решение |
|---|---|---|---|
| **Автокоррекция/подсказки** (v1) | Высокая (движок) или средняя (форк HeliBoard / свой простой префикс+Левенштейн) | Низкая: mmap-словарь 1–4 МБ, поиск единицы мс; HeliBoard работает на Android 4.4+ устройствах | Делать в v1 |
| **Свайп-ввод** | Очень высокая. В AOSP/HeliBoard **открытой реализации нет**: HeliBoard поддерживает glide typing только через подгрузку закрытой Google-библиотеки (`libjni_latinimegoogle.so`). FlorisBoard пишет свою — годы работы | CPU-нагрузка умеренная, но главное — трудозатраты и качество распознавания | «Потом» / скорее никогда своими силами. Честно: для татарского это огромная отдельная задача |
| **Эмодзи-панель** | Низкая-средняя (грид + категории + недавние; рендер системным шрифтом) | Осторожно с памятью: не раздувать — использовать `RecyclerView` с переиспользованием, рисовать эмодзи как текст (`StaticLayout`), не как 3000+ View. Поиск эмодзи по татарским словам — отдельная работа (нет данных) | v1. ~1–2 недели работы |
| **История буфера обмена** | Низкая (`ClipboardManager.addPrimaryClipChangedListener`, локальное хранение). Нюанс: с Android 10 фоновый доступ к буферу ограничен, но **IME с активным вводом имеет доступ**; на Android 13+ система показывает уведомление о чтении буфера | Почти нулевая | v1, дёшево и полезно |
| **Голосовой ввод** | Низкая, если **делегировать**: кнопка микрофона → `Intent(RecognizerIntent.ACTION_RECOGNIZE_SPEECH)` или переключение на голосовой IME через `InputMethodManager`/`switchInputMethod`. Писать своё распознавание — нереально | Нулевая (работа на стороне Google-сервиса) | Проблема не техническая: **поддержка татарского в системном распознавании Google не гарантирована** (публичных подтверждений полной поддержки tt-RU в SpeechRecognizer нет — проверить на устройстве). Если нет — кнопка бессмысленна. «Потом»; альтернатива в будущем — локальный Whisper-подобный движок, но это дорого для слабых устройств |
| **Next-word prediction (биграммы)** | Средняя (данные есть в формате .dict) | Низкая | «Потом», после автокоррекции |
| **Пользовательское обучение** (заучивание слов) | Средняя | Низкая (v4-словарь или своя SQLite) | v1 вместе с подсказками |

## 5. Итоговая приоритизация

**MVP (цель: 4–8 недель для новичка при своём коде; быстрее при форке)**
1. IME-каркас (`InputMethodService`), свой View клавиатуры (Canvas), subtypes tt/ru/en.
2. Раскладки: тат (доп. ряд `ә ө ү җ ң һ` + дублирующие long-press попапы — см. «Дополнение»), рус (с long-press на татарские буквы), en, слой цифр/символов ×2.
3. Shift/CapsLock/автокапитализация, backspace с автоповтором, Enter по imeOptions, двойной пробел = точка, свайп по пробелу = курсор.
4. Key preview попапы, хаптика, light/dark по системе.
5. Параллельно (не блокирует релиз): сбор корпуса, письмо в «Туган тел», сборка wordlist.

**v1**
1. Строка подсказок + автокоррекция (форк-движок HeliBoard или свой префикс+Левенштейн по частотному словарю).
2. Татарский словарь 150–250 тыс. форм (ttwiki + Leipzig + фильтр apertium-tat); русский и английский словари — готовые из aosp-dictionaries.
3. Заучивание пользовательских слов.
4. Эмодзи-панель, история буфера обмена.
5. Настройки: высота, звук/вибро, автокоррекция вкл/выкл.

**Потом**
- Next-word prediction (биграммы), морфологический предикшен для агглютинативных форм.
- Голосовой ввод (после проверки поддержки tt системным распознаванием).
- Свайп-ввод (только при наличии ресурсов/команды), темы, однорукий режим, стикеры.

**Ключевые риски**: (1) лицензия данных «Туган тел» не определена — закладывать fallback на Wikipedia+Leipzig; (2) если форкать HeliBoard — GPL-3.0 на весь продукт; (3) свайп и голос для татарского не имеют готовых открытых решений — не обещать пользователям.

## Дополнение (2026-07-18): единое решение по дефолтной татарской раскладке

Ранняя версия этого файла рекомендовала «10–11 клавиш + long-press попапы» как основной вариант — это противоречило выводам 05 (§3–4.5). Противоречие снято: **дефолт — дополнительный пятый ряд из 6 отдельных клавиш**, long-press остаётся дублирующим механизмом. Обоснование и конкретика ниже.

### Почему не long-press-only

- ә — 5-я по частоте буква татарского (6.65%), суммарно 6 доп. букв = 10.6% всех буквоупотреблений (05 §3). Long-press = ~300–500 мс + прицеливание в попап на каждой ~9-й букве — это прямое замедление основного сценария продукта.
- Прецедент с теми же буквами: казахское сообщество HeliBoard (issue Helium314/HeliBoard #2130) прямо формулирует «long-press popups slow down typing significantly» и предлагает extended-раскладку `[number_row] ё ә і ң ғ ү ұ қ ө һ` — доп. буквы верхним рядом, цифры под long-press. Автор issue собрал рабочий APK; статус — open/enhancement, в официальный релиз не влит (проверено 2026-07-18).
- «iOS-эстетика» не аргумент против доп. ряда: ломают эстетику **узкие клавиши в основной сетке** (вариант «12 в ряду»), а не отдельный ряд из 6 широких клавиш пониженной высоты — визуально он аналогичен ряду подсказок QuickType, который в iOS-стиле и так предусмотрен (04 §8).

### Дефолтная сетка (зафиксировано)

```
[доп. ряд]   ә  ө  ү  җ  ң  һ          ← 6 клавиш, высота ~0.75–0.8 буквенного ряда
[ряд 1]      й ц у к е н г ш щ з х      ← 11 клавиш
[ряд 2]      ф ы в а п р о л д ж э      ← 11 клавиш
[ряд 3]      ⇧ я ч с м и т ь б ю ⌫      ← shift + 9 + backspace
[ряд 4]      123  🌐  пробел  ⏎
```

- Порядок доп. ряда — алфавитно-мнемонический `ә ө ү җ ң һ` (легче искать глазами; рекомендация 05 §4.5). Вариант «по частоте» (`ә ү ң ө җ һ`) — на юзер-тест позже.
- Long-press-дубли на базовых клавишах: а→ә, о→ө, у→ү, н→ң, ж→җ, х→һ, э→ә, г→һ; в татарской раскладке пары ж/җ и э/ә можно инвертировать (05 §3 п.5) — но при наличии доп. ряда инверсия не обязательна, решить на этапе вёрстки.
- Цифры на доп. ряд **не** вешаем (в отличие от казахского proposal, где ряд 10-клавишный и совмещён с цифрами): у нас 6 клавиш ≠ 10 цифр, цифры остаются на слое `?123` как в iOS. Это проще и не перегружает ряд.
- Русская раскладка — стандартная ЙЦУКЕН без доп. ряда, но с теми же long-press-маппингами на татарские буквы.
- Опции в настройках (не MVP-блокер): «компактный режим» (скрыть доп. ряд, только long-press) и «Windows-раскладка» для старой школы.

### Проверка совместимости с iOS-геометрией (04)

Худший случай — экран шириной **320dp** (480×854 hdpi и т.п. бюджетники):

- Буквенные ряды по 11 клавиш: боковые отступы 3dp, зазор 4–5dp (04 прямо допускает ужать зазоры до 4–5dp для 11–12 клавиш) → ширина клавиши (320 − 2·3 − 10·4)/11 ≈ **25dp**. Это уровень русской ЙЦУКЕН в Gboard/Яндексе на том же экране и уровень iOS на iPhone SE (320pt, клавиша ~26pt) — приемлемо, ниже 320dp-экранов практически нет.
- Доп. ряд из 6 клавиш: (320 − 2·3 − 5·5)/6 ≈ **48dp** ширины — клавиши шире буквенных, промахи маловероятны даже при пониженной высоте.
- Высота. База 04: 4 ряда ≈ 200–216dp (минимум 200dp, целевое ~35% экрана). Доп. ряд ~36–40dp → **MVP-клавиатура ≈ 240–256dp**. На экране 320×533dp это ~45–48% высоты — терпимо, но на границе; поэтому высоту считать долей экрана с настройкой (04), а доп. ряд при нехватке места сжимать первым (до ~0.7 высоты буквенного ряда).

### Доп. ряд + ряд подсказок в v1: как совмещать

Конфликт «оба сверху» решается **стекированием**, а не заменой:

1. **Рекомендуемый вариант — стек**: `[подсказки ~40dp] → [доп. ряд ~36–40dp] → [4 ряда]`. Так работает связка «suggestion strip + number row» в Gboard и HeliBoard — оба элемента сосуществуют, ряд цифр/букв является частью раскладки, строка подсказок — отдельной панелью над ней. Итог в v1 ≈ 280–296dp на 320dp-экране (~50–55% высоты 533dp-экрана). Компенсации: (а) в v1 дать настройку высоты (04 §заключение); (б) подсказки урезать до 3 ячеек фиксированной высоты 40dp вместо 44–45; (в) на экранах <560dp высоты автоматически включать компактный доп. ряд 0.7×.
2. **Отвергнутый вариант — динамическая замена** (подсказки показываются на месте доп. ряда во время набора слова): выглядит экономно, но ломается на главном сценарии — ә/ө/ү нужны **в середине слова**, ровно когда ряд был бы скрыт подсказками. Плюс прыгающий UI. Не делать.
3. **Отвергнутый вариант — доп. буквы внутри строки подсказок** (буквы в пустых ячейках, подсказки вытесняют их при наборе): та же проблема, что в п. 2, плюс нестабильные тап-цели. Не делать.
4. Запасной вариант для маленьких экранов: настройка «скрывать доп. ряд при активных подсказках» — только как opt-in, не дефолт.

Практическое следствие для MVP: контейнер подсказок из 04 §8 («пустой контейнер фиксированной высоты») в MVP можно **не резервировать** — доп. ряд визуально занимает его роль «пятого элемента сверху», а в v1 строка подсказок добавится над ним, и общая высота вырастет один раз и предсказуемо.
