# Развитие Tatar Keyboard

## Решение

Следующий продуктовый майлстоун — D1: opt-in полоса из трёх татарских подсказок на
основе Leipzig top-100k. D0 показал 97.3318% покрытия принятых токенов и gzip-размер
около 582 КБ. Top-150k допустим только как offline comparator качества, но в D1 не
поставляется.

После завершения D1 порядок фиксирован: D2 — русский словарь, D3 — автозамена с
отменой. Персональный словарь, Zamanälif и пересмотр пятого ряда — позднее по спросу.

Пользовательский результат D1: при разрешённом татарском вводе над клавиатурой видны
до трёх частотных продолжений текущей словоформы. Тап явно заменяет введённый префикс
выбранной формой. Любой отказ словаря отключает только подсказки; обычный ввод всегда
остаётся рабочим.

## Устранённые D1e runtime-блокеры

- ✅ **HIGH — readiness/eligibility lifecycle.** Readiness callback сериализован через
  UI owner, запускает engine в уже активной eligible session и запрашивает текущий cached
  prefix; переход ineligible→eligible запускает engine. Поздний callback после destroy
  ничего не запускает и не запрашивает.
- ✅ **HIGH — atomic candidate binding.** Displayed candidates атомарно привязаны к
  exact displayed prefix/session. При переходе text A→text B binding старых A немедленно
  инвалидируется; tap(old A) после B — no-op и не может выполнить
  `commit(B, candidateA)`.
- ✅ **Hardening — warm-engine lifecycle re-entry.** При `tt→ru→tt` и при открытии
  нового eligible field уже опубликованный engine немедленно повторно запрашивает
  текущий известный непустой cached prefix. Cold и in-flight engine не получают
  дублирующий запрос: их единственный lookup выполняется после публикации engine.
- ✅ **Hardening — finished/preparing fail-closed state.** `onFinishInput` закрывает
  eligibility до позднего readiness callback; такой callback не запускает engine. При
  подготовке словаря или неуспешном engine полоса остаётся `GONE`/0dp и резервируется
  только после успешной публикации engine.

Реализованные детерминированные regression tests, закрывающие D1e:

- ✅ eligible start before prepare → readiness callback запускает engine и lookup текущего
  prefix;
- ✅ ineligible start → переход на tt subtype запускает engine и lookup текущего prefix;
- ✅ late readiness callback after destroy → engine/lookup не запускаются;
- ✅ `show(A) → text(B) → tap(old A)` → текст не изменяется;
- ✅ актуальный result B и tap(B) по-прежнему безопасно выполняют commit.
- ✅ `tt→ru→tt` с warm engine → текущий prefix запрашивается повторно без restart или
  cold-engine duplicate.
- ✅ readiness после `onFinishInput` → engine/lookup не запускаются, полоса остаётся
  скрытой.
- ✅ уже поставленный в очередь engine publish после `onFinishInput` → handle немедленно
  получает `finishInput`, lookup/reserve не выполняются.
- ✅ новый eligible field с retained warm engine → текущий cached prefix
  запрашивается ровно один раз без restart factory и без дополнительного keystroke.

Все пять обязательных тестов, `tapWithNothingDisplayedIsNoOp` и
`subtypeChangeToEligibleWithWarmEngineReRequestsCurrentPrefix`,
`eligibleStartWithWarmEngineReRequestsCurrentPrefix`, а также fail-closed тест
readiness после finish проходят; D1e закрыто.
Полная D1f artifact/device matrix остаётся открытой.

## Устранённые находки независимого аудита D1

Аудит подтвердил шесть дефектов; все закрыты и покрыты детерминированными JVM-тестами.

- ✅ **HIGH — tap-listener не переустанавливался при активации полосы через смену
  subtype.** Вью полосы инфлейтится лениво именно из `setTapListener`, а ветка
  ineligible-старта его не ставила, поэтому после переключения глобусом на татарский в
  уже открытом поле тап по кандидату ничего не делал. `onSubtypeChanged(eligible = true)`
  регистрирует listener заново (`subtypeChangeToEligibleRewiresTapListenerSoTapsStillCommit`).
- ✅ **HIGH — отсутствовала проверка буквы сразу после курсора.** Подсказка в середине
  слова портила текст. Добавлен правый контекст: `EditorSurface.hasLetterAfterCursor()`
  поверх `RichInputConnection.getCachedTextAfterCursor()` и чистого предиката
  `TatarWordUtils.startsWithWordCharacter` (первый кодпоинт: буква или комбинирующая
  метка). Контроллер при `true` не идёт в движок и оставляет пустую полосу,
  `InputLogic.commitChosenSuggestion` дублирует проверку fail-closed перед
  `deleteTextBeforeCursor`.
- ✅ **HIGH — контракт регистра не был реализован.** Добавлены
  `PrefixCasing`/`classifyCasing`/`applyCasing`: MIXED-префикс даёт 0 результатов без
  запроса к движку, регистр применяется к отранжированным кандидатам от `pendingPrefix`
  перед `showSuggestions`, а `expectedPrefix` остаётся сырым — показанная и вставленная
  строка совпадают.
- ✅ **MEDIUM — внутренние жесты курсора и свайп-удаления не гасили полосу.** Они идут
  через `RichInputConnection`, который сам держит expected selection, поэтому
  `onUpdateSelection` не видел внешнего перемещения. `onMoveCursorPointer`,
  `onMoveDeletePointer`, `onUpWithDeletePointerActive` и `onUpWithSpacePointerActive`
  теперь уведомляют контроллер напрямую через приватный
  `onSuggestionsAffectingCursorMove()`.
- ✅ **MEDIUM — TalkBack объявлял подсказки на каждое нажатие.** Объявление тройки
  выполняется только на переходе «пустая полоса → есть подсказки» и только при включённом
  touch exploration; сами слова остаются доступны через virtual nodes в любой момент.
- ✅ **MEDIUM — комбинирующие метки NFD обрывали границу слова.** Ряд слова продолжается
  через метки Mn/Mc/Me, орфанные метки без базовой буквы отбрасываются.

## Инварианты и бюджеты D1

- Функция работает только для татарского subtype, opt-in, default OFF.
- UI — один лениво создаваемый custom suggestion strip `View`: Canvas, 40dp, три равные
  ячейки и три стабильных virtual accessibility node ID; пустые nodes скрыты. Отдельных
  View на ячейку нет.
- В hot `draw`/`touch` пути — ноль аллокаций; janky frames ≤ 1%.
- Тап выполняет только явный `delete + commit`. Composing и автозамены в D1 нет.
- Новый Android-код — Kotlin с минимальным Java interop; новых зависимостей и NDK/JNI нет.
- Распаковка, checksum, mmap и lookup не выполняются на UI/cold-start пути.
- Prefix lookup compute p95 ≤ 5 мс; полный request→publish warm p95, включая очередь и
  UI dispatch, ≤ 16 мс; показанных stale results — 0.
- Сжатый asset ≤ 700 КБ; распакованный словарь ≤ 2.8 MiB.
- Целевой APK после D1 ≤ 1.7 МБ; абсолютный hard limit ≤ 3 MiB.
- Total PSS показанной клавиатуры ≤ 30 МБ; холодный старт < 400 мс.
- INTERNET permission, сетевые операции, аналитика и логирование введённого текста
  отсутствуют.
- Исходные корпусные архивы и `words.txt` не хранятся в проекте.

Превышение hard limit, privacy breach, изменение текста при stale state или поломка
обычного ввода — безусловный no-go.

Фактическое состояние бюджетов: APK 1 446 111 байт — в пределах и hard limit, и целевых
1,7 МБ; холодный старт на эмуляторе 124–147 мс; PSS на эмуляторе выходит за 30 МБ и
требует перезамера на реальном устройстве; latency, allocation и jank на железе не
измерялись. Подробности и оговорки — в разделе D1f.

## Контракт текста

- Boundary-анализ выполняется прямо по сырому тексту snapshot, без промежуточной
  нормализации: ряд слова продолжается через комбинирующие метки (Mn/Mc/Me), поэтому
  канонически разложенный (NFD) ввод не обрывает слово, а результат остаётся точным span
  исходного текста — именно это делает удаление безопасным. Нормализация к NFC
  выполняется отдельно, уже на этапе lookup.
- Текущий префикс — максимальная непрерывная последовательность букв татарского
  кириллического алфавита непосредственно перед collapsed cursor. Классификация
  выполняется по `Character.isLetter`, то есть шире алфавита (латиница и русская
  кириллица тоже считаются буквами); такие префиксы просто не находятся в словаре и дают
  0 результатов.
- Пробел, цифра, пунктуация, дефис, апостроф и любой символ вне алфавита завершают слово.
  Комбинирующая метка без базовой буквы словом не считается: ведущие орфанные метки
  отбрасываются, а ряд без единой буквы даёт пустой префикс.
- При selection, пустом префиксе или букве сразу после cursor результаты очищаются: ввод
  в середине слова и замена выделения не поддерживаются. Реализация намеренно шире
  контракта и fail-closed: границей считается любая буква (в том числе латинская и
  русская) и любая комбинирующая метка сразу после курсора — слишком узкая проверка
  портит текст, слишком широкая лишь не показывает подсказку.
- Для lookup префикс приводится к NFC и lowercase. Словарь хранит NFC lowercase.
- Все lowercase-буквы дают lowercase формы. Одна заглавная буква либо первая заглавная
  и остальные lowercase дают Initial Caps. Две и более заглавные без lowercase дают
  ALL CAPS. Любой другой смешанный регистр даёт 0 результатов.
- Отображаемая и вставляемая форма имеют одинаковый регистр.
- Форма, в точности равная уже набранному нормализованному слову, исключается; более
  длинные формы с тем же префиксом остаются кандидатами.
- Кандидаты ранжируются по frequency descending, затем по Unicode code-point lexical
  ascending. Регистр отображения применяется только после ранжирования.
- Перед тапом повторно проверяются editor session, collapsed selection, subtype, generation,
  отсутствие буквы сразу после курсора и точный префикс. Удаление выполняется по code
  points; несовпадение отменяет действие.
- Принятая подсказка вставляется вместе с завершающим пробелом — одним `commitText` в том
  же batch edit, что и удаление префикса, поэтому промежуточное состояние «слово без
  пробела» пользователю не показывается. Пробел не добавляется, если текст сразу после
  курсора уже отделяет слово: первый кодпоинт — пробельный символ (включая tab, перевод
  строки и неразрывный пробел) либо примыкающая к слову пунктуация (категории Unicode
  Pc/Pd/Ps/Pe/Pi/Pf/Po, то есть в том числе «», тире, многоточие и типографские кавычки),
  чтобы «сүз,» не превращалось в «сүз ,». Цифра, математический символ (Sm: «2 + 2»),
  emoji и конец текста пробел получают. Вставленный пробел не взводит жест «двойной пробел
  → точка»: следующее нажатие пробела ведёт себя как первое. После успешного коммита
  shift-состояние пересчитывается тем же вызовом, что и после обычного набранного символа,
  поэтому автозаглавная видит вставленное слово с пробелом сразу, не дожидаясь
  `onUpdateSelection`.

Фактическое покрытие этих правил тестами:

- границы слова — `TatarWordUtilsTest`: татарские буквы, русская кириллица, смешанные
  скрипты, пробел/цифра/пунктуация, NFD (метка внутри слова, слово, оканчивающееся
  меткой, разложенное «ё», орфанная метка) и совпадение возвращённого span с сырым
  текстом;
- регистр — `TatarWordUtilsTest` (`classifyCasing`/`applyCasing`, включая caseless-метки и
  round-trip «классифицировать → применить») плюс сквозные
  `SuggestionsControllerTest.lowerCasePrefixShowsAndCommitsDictionaryFormUnchanged`,
  `initialCapsPrefixShowsAndCommitsInitialCapsForms`,
  `allCapsPrefixShowsAndCommitsAllCapsForms`, `mixedCasePrefixYieldsNoRequestAndAnEmptyBand`;
- курсор внутри слова — `TatarWordUtilsTest.startsWithWordCharacter*` (пусто, пробел,
  запятая, перевод строки, цифра, дефис, emoji, буква, ведущая метка) и

## D1a — формат, generator и финальный top-100k asset

### Scope и deliverable

- Из закреплённых Leipzig `mixed/news/web` выбрать top-100k по frequency descending,
  затем Unicode code-point lexical ascending, после чего пересортировать весь срез
  только в code-point lexical order для binary prefix search.
- Зафиксировать versioned binary contract: magic/schema, count, offsets, UTF-8 word blob,
  u32 frequencies и checksum.
- Добавить воспроизводимый generator, строгий validator, свободно созданные fixtures и
  реальный сжатый top-100k asset.
- Вместе с asset зафиксировать CC BY 4.0 attribution/NOTICE, source URL, corpus
  version/date и полный transformation record.
- На независимом held-out наборе сравнить 50k/100k/150k; 150k используется только в
  локальной оценке.

### Fail-closed acceptance

- Одинаковые входы и версия generator дают байт-в-байт одинаковый asset.
- Malformed input, duplicate, несортированность, overflow, неверная schema или checksum
  завершают генерацию/валидацию ошибкой.
- Asset и распакованный файл укладываются в 700 КБ / 2.8 MiB.
- Coverage top-100k отстаёт от 150k на held-out не более чем на 1 процентный пункт;
  ручной татарский query-set не выявляет систематический русский/технический мусор.
- No-go: невоспроизводимость, неясное происхождение/условия данных или провал size/quality.

## D1b — compressed storage и безопасная смена версии

> Автоматизируемое ядро и отдельная APK delta зафиксированы в
> `docs/DICTIONARY-D1B.md`. JVM/build/privacy gates зелёные, но физические direct-boot,
> power-loss/no-space и startup проверки остаются в D1f; полная device acceptance здесь не
> заявляется.

### Scope и deliverable

- Background pipeline: asset → temp-файл в device-protected `filesDir` → flush/fsync →
  size/checksum/schema validation → atomic rename.
- Новую versioned file полностью валидировать и атомарно публиковать, но не активировать
  вместо живого mapping. Активация разрешена только в следующем безопасном IME lifecycle,
  когда старый executor остановлен и readers отсутствуют.
- Kotlin storage component и тесты first run, повторного запуска, обновления, corruption,
  оборванной записи, нехватки места и direct boot.

### Fail-closed acceptance

- После прерывания доступен прежний валидный файл либо никакой; partial не становится final.
- Ошибка отключает подсказки и не задерживает показ/обычный ввод.
- Нет I/O, checksum или mmap на UI thread; cold start остаётся < 400 мс.
- На диске сохраняются не более current и одной staged/old version; active/current файл
  не удаляется.
- No-go: недоказанная атомарность/direct-boot безопасность или нарушение size/startup.

## D1d — mmap prefix engine и bounded threading

### Scope и deliverable

- Binary prefix range по mmap; exact typed word исключается; top-3 ранжируется по
  frequency descending, затем Unicode code-point lexical ascending.
- Один bounded latest-only/coalescing executor: максимум один running и один latest
  pending request; промежуточные запросы заменяются, очередь не растёт.
- Generation включает editor session, subtype, prefix и dictionary version; publish
  разрешён только при полном совпадении.
- `FileChannel` закрывается сразу после read-only `map`. Активный mapping immutable и не
  hot-swap-ится в живом engine session; новая опубликованная версия выбирается только в
  следующем safe lifecycle до запуска readers.
- Finish input очищает pending work и инвалидирует generation. Destroy дополнительно
  останавливает executor; strong references на mapping сбрасываются только после readers.
  Фактический unmap GC-dependent и не считается управляемой операцией public API minSdk 24.
  Старый versioned file удаляется только когда он не active/current.

### Fail-closed acceptance

- Compute p95 ≤ 5 мс, request→publish p95 ≤ 16 мс, stale publish = 0.
- Burst/race tests доказывают bounded queue, coalescing, subtype/editor/version guards и
  отсутствие use-after-switch.
- Repeated lifecycle tests подтверждают: open FD не растут, retained disk ≤ current + одна
  staged/old version, PSS не растёт без границ; hot-swap mapping не происходит.
- Ranking tests подтверждают exact-word exclusion и frequency-desc/code-point-lexical ties.
- Corrupt/no-match/empty input возвращает 0 результатов без влияния на ввод.
- No-go: unbounded backlog, lifecycle leak, use-after-close, stale result или latency miss.

## D1e — интеграция, настройка, privacy и accessibility

### Scope и deliverable

- Eligibility: татарский subtype, готовый словарь и
  `InputAttributes.mShouldShowSuggestions == true`.
- Сохраняются gates для password, email, URI, filter, `NO_SUGGESTIONS` и autocomplete.

- Реализуются state table, текстовый контракт, безопасный тап `delete + commit` и
  accessibility announcements.

### Fail-closed acceptance

- При OFF/privacy/non-tt словарь не запрашивается, полоса `GONE`, текст не логируется.
- Смена subtype/editor/selection немедленно очищает UI и инвалидирует запросы.
- Stale tap или рассинхрон кэша не меняет текст.
- Полная editor/privacy matrix, word-boundary/casing и TalkBack tests зелёные.
- Все пять детерминированных regression tests из раздела runtime-блокеров обязательны и
  зелёные; дополнительные no-op, warm-engine subtype-return и late readiness/publish
  after finish тесты также зелёные. Без них D1e не выполнено, а D1f, merge и release
  запрещены.
- No-go: обход gate, default не OFF или изменение текста без повторной валидации.

Порядок фаз после D1 согласован с владельцем и зафиксирован ниже отдельным разделом

- E2 — панель эмодзи без собственного шрифта.
- E3 — устойчивость подсказок к опечаткам (нечёткий префикс на одно редактирование).
- D2: отдельный русский словарь на той же архитектуре, только при сохранении общего

  «boolean eligible → идентификатор активного subtype».
- E4 — личный словарь, привязанный к активному subtype.
- E5 — предсказание следующего слова (биграммы) с ранним гейтом по размеру.
- D3: отдельная opt-in автозамена без composing; немедленный backspace восстанавливает

## План после D1: E1 → E2 → E3 → D2 → E4 → E5

Порядок фиксирован: **E1** (ленивая подготовка словаря и одноразовое предложение включить
подсказки) → **E2** (панель эмодзи) → **E3** (устойчивость подсказок к опечаткам) →
**D2** (русский словарь) → **E4** (личный словарь) → **E5** (предсказание следующего
слова). D3 остаётся после них и своего контракта здесь не получает.

Почему D2 стоит посередине, а не последней: E4 и E5 — первые фазы, которые заводят
собственные пользовательские данные и собственное ранжирование. Если они появятся до
второго языка, их хранилище, ключи и правила слияния придётся переписывать при добавлении
русского — ровно та работа, которой сквозное решение о привязке к subtype и должно
избежать. Поэтому D2 идёт раньше них и владеет рефакторингом «boolean eligible →
идентификатор активного subtype». E1–E3 нового пользовательского хранилища не заводят
(единственное объявленное исключение — «недавние» эмодзи в E2), поэтому безопасно стоят
до D2.

Общий per-phase gate D1a–D1e действует без изменений для всех фаз и подфаз E1–E5: сборка,
релевантные быстрые тесты подфазы, no-INTERNET check на собранном artifact, записанная APK
delta. Дополнительно для этих фаз:

- **APK-бюджет фазы выражается только как дельта** к ИЗМЕРЕННОМУ артефакту непосредственно
  предыдущей фазы плюс абсолютный hard limit 3 145 728 Б. Абсолютные числа, посчитанные от
  1 446 111 Б, в приёмке последующих фаз не используются: в согласованном порядке фаз они
  недостижимы арифметически и дали бы красный gate по причине, не связанной с качеством
  работы.
- **Базис регресса — набор тестов, зафиксированный на входе фазы.** На входе E1 это 186
  тестов; дальше набор растёт, поэтому фактическое число на входе и на выходе записывается
  в docs фазы, а «186» как абсолютное требование больше не цитируется.
- Каждая подфаза заканчивается собирающимся release-APK. Провал любого условия запрещает
  коммит и переход к следующей подфазе.
- Ни одна фаза E1–E5 не меняет замороженные контракты D1 молча. Любая правка разделов
  «Состояния полосы» и «Контракт текста» вносится письменно и отревьюирована ДО написания
  кода фазы; фазы, которым это нужно, перечисляют правки в своём scope (E3, E4, E5).

## Сквозное решение: всё новое ключуется активным subtype

Это решение обязательно к соблюдению во всех фазах и не может быть отложено «до D2».

- Любое новое хранилище, счётчик, снапшот, таблица и запрос параметризованы
  идентификатором активного subtype (например `tt_RU`) с самого начала: путь на диске, имя
  файла, тег внутри файла, ключ снапшота в памяти и алфавитный фильтр. Общего
  «дефолтного» хранилища нет ни у одной фазы. Для subtype без объявленного алфавита фича
  выключается целиком, а не деградирует к чужому языку.
- Владелец рефакторинга «boolean eligible → идентификатор активного subtype» — **D2, и
  только D2**. E1 и E3 продолжают жить с существующим литералом
  `SuggestionsController.SUBTYPE_ID = "tt_RU"`, который сейчас согласован с таким же
  литералом в `LatinIME.isTatarSuggestionsEligible()`; E4 и E5 — потребители уже готового
  шва. После D2 guard по несовпадению subtypeId перепроверяется отдельным тестом в каждой
  фазе, которая его читает.
- **Единая граница освобождения движка.** Любое событие, требующее другого mapping (смена
  настройки подсказок, смена subtype, смена языка словаря), немедленно закрывает
  eligibility — полоса `GONE`, generation инвалидирована, displayed candidates отвязаны,
  новых lookup нет, — а блокирующие `releaseEngine` + `start` выполняются только на
  следующей границе `onFinishInputView`/`onStartInput`. Причина: `destroyHandle` блокирует
  UI-поток до 60 мс и при неудаче ещё до 180 мс, то есть до 240 мс на нажатие глобуса.
  Правило вводит E1a-6 и охраняет source-contract тестом; D2, E4 и E5 обязаны его
  соблюдать. Отложенное освобождение отменяется, если к моменту границы условие вернулось
  и живой движок по-прежнему корректен.
- Объявленное исключение ровно одно: список «недавних» эмодзи в E2 не ключуется по
  subtype, потому что набор эмодзи языконезависим. Любое другое отступление требует
  письменной поправки этого раздела, а не решения внутри фазы.
- Флаг «предложение включить подсказки израсходовано» (E1b) — один глобальный ключ, а не
  ключ на язык. После D2 предложение не показывается повторно для второго языка и флаг для
  него не переиспользуется; отдельное предложение для русского — при необходимости
  отдельная будущая фаза.

## Бюджет памяти (PSS): сквозной реестр

Связывающее ограничение проекта — память, и оно **уже провалено**.

- Измерено (эмулятор API 35, swiftshader; достоверна дельта, не абсолюты): 33,4–33,6 МБ с
  включённой D1 против 29,2–29,4 МБ с выключенной при бюджете **30 МБ**, то есть D1 стоит
  ≈ **+4,2 МБ** PSS. Корректного замера на реальном железе нет (открытый пункт D1f).
- Заявленные дельты будущих фаз: E2 ≤ 3,0 МБ при открытой панели; E4 ≤ 0,5 МБ при 2 000
  личных записей; E5 ≤ 1,5 МБ на вторую mmap-таблицу; D2 ≈ +4,2 МБ по аналогии с D1
  (расчёт, не измерение). Сумма с текущим состоянием — ориентировочно **42,7 МБ** против
  бюджета 30 МБ.
- Правило: пока корректный перезамер D1f на реальном устройстве не выполнен, ни одна фаза
  не имеет права объявлять абсолютный PSS пройденным. Каждая фаза измеряет и записывает
  свою дельту A/B в одном прогоне на одном устройстве и не ухудшает состояние сверх
  заявленной дельты.
- Требуется письменное решение владельца, зафиксированное в `docs/MILESTONE-v2.md`: либо
  перезамер D1f становится блокирующим входом в E2, либо потолок 30 МБ пересматривается с
  обоснованием и новым числом. См. раздел открытых вопросов; это решение блокирует вход в
  E2b-1 и в E5d.

## E1 — ленивая подготовка словаря и одноразовое предложение включить подсказки

Пользователь, который никогда не включал татарские подсказки (состояние по умолчанию),
перестаёт за них платить: словарь не распаковывается и не валидируется при старте
клавиатуры вообще. Пользователь, который о подсказках не знает, ровно один раз получает
ненавязчивое предложение их включить; включение и выключение действуют сразу, без
перезапуска клавиатуры. Подфазы: E1a (ленивость), E1b (предложение), E1c (свидетельства),
E1d (условная — кэш валидации).

### Scope и deliverable

- **E1a-1.** `SuggestionsController.onCreate()` перестаёт создавать фоновый executor,
  storage-контроллер и вызывать `prepare()`. Из `onCreate` остаётся только регистрация
  tap-listener; всё остальное создаётся лениво.
- **E1a-2. Жизненный цикл флага «подготовка запрошена» — единственная формулировка,
  отменяющая любые другие.** Подготовка запрашивается по первому из двух событий: (а)
  переход `PREF_TATAR_SUGGESTIONS` OFF→ON, наблюдаемый живым IME; (б) первый переход
  контроллера в eligible. Флаг ставится в момент запроса. После `PreparationResult.
  Published` флаг **не сбрасывается никогда** (`dictionaryReady` остаётся выставленным,
  engine поднимается из уже опубликованного файла). Флаг сбрасывается **только** если
  последний известный результат — `PreparationResult.Unavailable` И наблюдён новый переход
  OFF→ON. Собственной дедупликации ниже нет: `DictionaryStorageController.prepare` —
  прямой делегат, а `BackgroundDictionaryPreparer.prepare` на каждый вызов кладёт новую
  задачу в single-thread executor, поэтому флаг — единственный guard.
- **E1a-3.** Ленивая подготовка вынесена за отдельный инъектируемый шов (по образцу
  `UiPoster` и `engineFactory`), чтобы «prepare не запрошен / запрошен ровно один раз»
  проверялось JVM-тестом без Android.
- **E1a-4. Канал «настройка изменилась → живой IME».** `LatinIME` регистрирует
  `SharedPreferences.OnSharedPreferenceChangeListener` на device-protected prefs
  (`PreferenceManagerCompat.getDeviceSharedPreferences`) и снимает его в `onDestroy()`
  рядом с `mSettings.onDestroy()`. Слушатель **хранится в поле** `LatinIME`:
  `SharedPreferencesImpl` держит слушателей в `WeakHashMap`, поэтому анонимная лямбда без
  strong reference молча собирается GC и канал умирает без единого симптома. Обработчик
  переносит `key == null` (так его зовёт `Settings.onReceive`), хранит последнее известное
  значение настройки, реагирует только на фактическое изменение и не выполняет тяжёлой
  работы.
- **E1a-5. Выключение в живом IME.** Отдельный явный метод контроллера: полоса уходит в
  `GONE`, eligibility закрывается, in-flight generation инвалидируется, displayed
  candidates отвязываются, новых lookup нет. Переиспользовать `onSubtypeChanged()` под
  смену настройки запрещено.
- **E1a-6. Включение в живом IME — симметричный явный метод.** Он обязан: пересчитать
  eligibility через `LatinIME.isTatarSuggestionsEligible()`; заново зарегистрировать
  tap-listener (полоса инфлейтится лениво именно из `setTapListener` — это закрытая
  HIGH-находка аудита D1, без переустановки тап не сработает); при warm engine вызвать
  `reserve()` и переиспользовать существующий путь повторного запроса
  «engineWasReady && hasKnownCursor && cachedWordBeforeCursor().isNotEmpty() →
  requestCurrentPrefix()»; при холодном или неготовом словаре оставить полосу `GONE` и
  запросить подготовку по правилу E1a-2. Без этого метода eligible не выставляется никем:
  смена `SharedPreferences` не вызывает ни `onStartInput`, ни `onSubtypeChanged`, а второй
  readiness-callback по E1a-2 запрещён.
- **E1a-7. Отложенное освобождение.** `releaseEngine()` выполняется НЕ в обработчике
  настройки, а на следующей границе lifecycle (`onFinishInputView` / `onStartInput`).
  Он не выставляет `destroyed`, не гасит фоновый executor, обнуляет `engine` только при
  успешном релизе, при неудаче повторяет попытку на следующей границе и до успеха не
  создаёт новый engine. Отложенное освобождение **отменяется**, если к моменту границы
  настройка снова ON и живой движок корректен. Это правило — источник общего инварианта
  раздела «Сквозное решение».
- **E1a-8. Опубликованный `.tdict` при выключении не удаляется.** Главный выигрыш даёт
  сама ленивость: у выключивших по умолчанию файл не появляется вообще. Удаление
  потребовало бы нового destructive-пути в хранилище (публичный purge с проверкой lease,
  гонки enable/disable, power-loss) ради 2 542 036 Б, спорило бы с формулировкой D1b
  «active/current файл не удаляется» и делало бы повторное включение дорогим. Штатный
  способ вернуть место у пользователя есть — удаление данных приложения.
- **E1a-9.** `PreparationResult.Unavailable` терминален для текущего enable-цикла: полоса
  остаётся `GONE`/0dp, обычный ввод не затронут, пользователю ничего не показывается,
  ничего не логируется; новая попытка возможна только по правилу сброса флага из E1a-2.
- **E1a-10. Engine-фабрика.** Перестаёт создавать второй `AtomicDictionaryStore` и
  одноразовый executor на каждый старт engine: используется уже объявленный, но
  неиспользуемый шов `SuggestionsController.engineCatalog()`;
  `MappedEngineHandle.create(Context, ResultCallback)` уходит, остаётся
  `start(catalog, callback)`. Каталога может не быть вообще (storage создаётся лениво):
  тогда фабрика возвращает `null`, `publishEngine(null)` оставляет полосу `GONE`, обычный
  ввод не затронут — fail-closed, без исключений и логов.
- **E1b-1.** Новый ключ «предложение израсходовано» в тех же device-protected prefs рядом
  с `PREF_TATAR_SUGGESTIONS`, с reader/writer по образцу `readTatarSuggestionsEnabled` /
  `writePrefCurrentSubtype`. В `SettingsValues` не кладётся (объект пересоздаётся целиком
  на каждое изменение любой настройки) и в whitelist enterprise-restrictions не
  добавляется.
- **E1b-2.** Предложение — модальный `AlertDialog` по существующему в проекте образцу:
  поле `mOptionsDialog`, `isShowingOptionDialog()`, гашение в `hideWindow()`,
  `lp.token = getMainKeyboardView().getWindowToken()`, `TYPE_APPLICATION_ATTACHED_DIALOG`,
  `FLAG_ALT_FOCUSABLE_IM`, тема через `DialogUtils.getPlatformDialogThemeContext`. В полосу
  подсказок фаза не рисует ничего и `input_view.xml` не трогает.
- **E1b-3.** Две кнопки: «Включить» пишет `PREF_TATAR_SUGGESTIONS = true` (и через канал
  E1a-4/E1a-6 подсказки включаются в текущем поле) и «Не сейчас». Отмена касанием вне
  диалога и системной кнопкой «назад» разрешена и равносильна «Не сейчас».
- **E1b-4.** Флаг расходуется в момент решения показать — одной записью до `dialog.show()`,
  а не по ответу пользователя. Ни ответ, ни поворот, ни скрытие окна, ни смерть процесса,
  ни перезагрузка флаг не возвращают. Направление отказа выбрано осознанно: допустимо
  показать ноль раз, недопустимо два.
- **E1b-5.** Условия показа, все обязательны: настройка OFF; флаг не израсходован; активный
  subtype татарский; input view показан и window token непустой; поле обычное
  (`mInputAttributes.mShouldShowSuggestions == true`); устройство разблокировано; другой
  диалог не показан; IME не подавлен аппаратной клавиатурой. Точки проверки —
  `onCurrentSubtypeChanged()` и `onStartInputViewInternal()`: пользователь с единственным
  татарским subtype перехода на татарскую раскладку не совершает вообще.
- **E1b-6.** Заблокированное устройство (direct boot, `UserManager.isUserUnlocked()`
  ложно): предложение не показывается и флаг НЕ расходуется — оно откладывается до первого
  подходящего момента после разблокировки. Работа подсказок в direct boot не меняется.
- **E1b-7.** Строки диалога — en base, ru и tt по образцу D1e; татарская формулировка
  добавляется в список к вычитке носителем языка перед релизом.
- **E1c.** Свидетельства обеих подфаз записываются в `docs/DICTIONARY-E1.md` по образцу
  `docs/DICTIONARY-D1E.md`: APK delta к измеренному артефакту на входе, измеренные времена,
  что проверено на реальном устройстве и что не проверено вообще.
- **E1d (условная подфаза, включается по измерению).** Порог «тумблер → полоса» и «первое
  татарское поле → полоса» согласуется с владельцем ДО начала E1a (предложение —
  p95 1 000 мс, число утверждает владелец). Если измеренное на реальном устройстве время
  порог превышает, кэширование результата валидации между `prepare()` и
  `acquireLatestForActivation()` становится обязательной подфазой E1d, а не идеей на потом:
  сейчас `TdictValidator.validateRaw` выполняется дважды на первое включение — два SHA-256
  по 2,5 МБ и построчная проверка 100 000 слов каждый раз.

### Fail-closed acceptance

- Свежая установка, настройка ни разу не включалась: после не менее 5 минут ввода (русское
  и татарское поле, смена полей, поворот, скрытие и показ клавиатуры) каталог
  `dictionaries` в device-protected `filesDir` отсутствует или пуст. Проверка — `run-as` на
  debug-сборке; на release эквивалент — рост раздела «Данные» приложения менее 0,5 МБ.
- JVM: при eligible == false и настройке OFF подготовка не запрашивается ни разу,
  storage-контроллер и фоновый executor не создаются.
- JVM: первый переход в eligible запрашивает подготовку ровно один раз; десять последующих
  `onStartInput`/`onSubtypeChanged` дают ноль новых запросов.
- JVM (флаг, тест «а»): `Published` → OFF→ON → **ноль** новых запросов подготовки.
- JVM (флаг, тест «б»): `Unavailable` → OFF→ON → **ровно один** новый запрос; без нового
  OFF→ON — ноль при любом числе `onStartInput`/`onSubtypeChanged`.
- JVM: disable → enable в том же editor session при warm engine → **ровно один** запрос
  текущего префикса, без restart фабрики и без дополнительного нажатия клавиши (образец —
  существующие `eligibleStartWithWarmEngineReRequestsCurrentPrefix` и
  `subtypeChangeToEligibleWithWarmEngineReRequestsCurrentPrefix`).
- JVM: после освобождения engine повторное включение поднимает engine без повторного
  запроса подготовки.
- JVM: `engineCatalog()` вернул `null` → фабрика возвращает `null`, полоса `GONE`, обычный
  ввод не затронут, исключение наружу не выходит.
- JVM: отложенное освобождение отменяется — disable → enable → `onStartInput` не вызывает
  `releaseEngine`, движок остаётся живым.
- Source-contract: в обработчике изменения настройки нет вызова `destroy`/`releaseEngine`;
  блокирующий путь освобождения вызывается только из `onFinishInputView`/`onStartInput`;
  обработчик переносит `key == null`; слушатель хранится в поле и снимается в
  `LatinIME.onDestroy`.
- Устройство: включение тумблера при открытой клавиатуре даёт полосу в том же editor
  session, без перезапуска IME и без дополнительного нажатия клавиши; измеренное время
  «тумблер → полоса» записано в docs и сопоставлено с порогом E1d.
- Устройство: выключение тумблера при открытой клавиатуре гасит полосу без дополнительных
  касаний — `contentTopInsets` возвращается к значению «без полосы» (для density 440 это
  1294 против 1184); после выключения не выполняется ни один lookup.
- Устройство: после освобождения на следующей границе lifecycle в `/proc/<pid>/fd` нет
  открытых дескрипторов на `.tdict`; повторное включение открывает ровно один. Падение PSS
  в приёмку не входит: фактический unmap GC-зависимый (D1d).
- Устройство: force-stop процесса и открытие татарского поля при включённой настройке и
  уже опубликованном файле дают подсказки без повторной распаковки — имя и mtime файла не
  меняются.
- Холодный старт до показа клавиатуры < 400 мс и не хуже зафиксированных 124–147 мс на том
  же стенде; при настройке OFF фоновой словарной работы нет вообще — ни распаковки, ни
  SHA-256, ни построчной валидации 100 000 слов.
- E1b: диалог показывается ровно один раз — показать → «Не сейчас» → десять раз сменить
  поле и раскладку → force-stop → перезагрузка устройства; после этого он не появляется ни
  разу.
- E1b: «Включить» приводит к `PREF_TATAR_SUGGESTIONS == true` и к появлению полосы в
  текущем поле без перезапуска клавиатуры.
- E1b: «Не сейчас», касание вне диалога, кнопка «назад» и скрытие окна оставляют настройку
  OFF; текст пользователя не меняется ни при одном ответе.
- E1b: диалог не показывается при уже включённой настройке; в поле пароля; в поле с
  `NO_SUGGESTIONS`; при подавлении IME аппаратной клавиатурой; когда показан другой диалог;
  когда window token отсутствует.
- E1b: direct boot — на заблокированном устройстве диалог не показан и флаг не
  израсходован; после разблокировки он показывается один раз.
- E1b: `hideWindow()` гасит диалог и обнуляет ссылку тем же путём, что `mOptionsDialog`;
  повторный показ клавиатуры диалог не воскрешает.
- E1b: таблица состояний полосы не изменена ни одной строкой — при настройке OFF полоса
  `GONE`/0dp до, во время и после диалога; ни ячеек, ни virtual accessibility node фаза не
  добавляет.
- E1b: обновление приложения — пользователь с уже включёнными подсказками предложения не
  получает никогда; пользователь с выключенными получает его один раз при первом татарском
  вводе после обновления.
- E1b: строки присутствуют в en base, ru и tt; отсутствие перевода даёт fallback на base,
  а не крэш. Source-contract или JVM: запись флага выполняется до `show()` и ровно одна, в
  обработчиках ответа записи флага нет.
- Набор тестов, зафиксированный на входе фазы (186), зелёный; изменённые и добавленные
  тесты перечислены с причиной; no-INTERNET check на собранном artifact пройден; APK delta
  ≤ 14 336 Б к измеренному артефакту на входе, записана вместе с остатком до 3 145 728 Б.
- Любой отказ подготовки, освобождения или диалога оставляет обычный ввод полностью
  рабочим и не меняет текст пользователя.
- No-go: словарь распаковывается или валидируется при выключенной настройке; включение или
  выключение требует перезапуска клавиатуры; освобождение блокирует UI-поток в обработчике
  изменения настройки; полоса видима или резервирует высоту при настройке OFF либо при
  подготовке словаря; предложение показано дважды, показано в password-поле или до
  разблокировки устройства, либо включает подсказки без явного действия пользователя;
  отказ подготовки, освобождения или диалога ломает обычный ввод или меняет текст.

## E2 — панель эмодзи без собственного шрифта

Пользователь вводит эмодзи прямо из клавиатуры: отдельная панель на месте букв с
категориями и «недавними», возврат к буквам одной клавишей, удаление стирает эмодзи
целиком. Свой шрифт не поставляется — рисуем системным, и то, чего в системном шрифте нет,
панель не показывает вообще, поэтому «тофу»-квадратов пользователь не видит ни на одной
прошивке. Подфазы: E2a (данные и удаление), E2b-1 (клавиша, коды, поверхность и insets),
E2b-2 (снапшот, сетка, вставка), E2b-3 (fling и «недавние»), E2c (a11y, устойчивость,
gates).

**Блокирующий вход в E2b-1:** письменное решение владельца по PSS (перезамер D1f на железе
либо пересмотр потолка 30 МБ с новым числом), зафиксированное в `docs/MILESTONE-v2.md`.
Без него фаза добавляет вторую полноэкранную поверхность в бюджет, который не измерен.

### Scope и deliverable

- **E2a.** `scripts/emoji_pack.py` — воспроизводимый генератор на чистом stdlib по образцу
  `scripts/dictionary_pack.py`: вход — локально скачанный `emoji-test.txt` закреплённой
  версии Unicode с зафиксированным SHA-256, выход — детерминированный текстовый asset
  `app/src/main/assets/emoji/emoji_set_v1.txt`. Исходный файл Unicode в репозиторий не
  коммитится; в проект попадают только сгенерированный asset, `assets/emoji/NOTICE.txt` с
  лицензией и атрибуцией Unicode и transformation record в `docs/DICTIONARY-E2.md`.
- **E2a.** Формат asset — данные, а не код: UTF-8, LF, одна последовательность в строке,
  секции категорий строками вида `#smileys`, порядок внутри секции — порядок
  `emoji-test.txt` для fully-qualified записей; дубликаты и посторонние строки запрещены.
  Guardrail: распакованный asset ≤ 65 536 Б и ≤ 1 400 записей, иначе генератор падает с
  ненулевым кодом. Хранение именно в `assets/`, а не в строковых ресурсах:
  `resources.arsc` лежит в APK методом Stored и стоил бы полный несжатый размер.
- **E2a.** `EmojiSet.kt` — чистый Kotlin-парсер asset в неизменяемый снапшот «категории →
  записи». Fail-closed: нарушенная строка отбрасывается, полностью нечитаемый вход даёт
  пустой набор, исключение наружу не выбрасывается.
- **E2a.** `GlyphProbe` — интерфейс `hasGlyph(sequence: String): Boolean`; продакшн поверх
  `Paint.hasGlyph`, тестовая реализация — фейк. Фильтрация набора по пробе и компоновка
  категорий выполняются один раз при построении снапшота, а не при отрисовке.
- **E2a.** `EmojiTextUtils.kt` — чистая `trailingEmojiClusterLength(text: CharSequence):
  Int`, возвращающая число java-`char` для удаления одним backspace. Покрываемые классы:
  суррогатная пара, VS15/VS16, модификаторы тона кожи U+1F3FB–U+1F3FF, ZWJ, keycap,
  пара региональных индикаторов, tag-последовательность с терминатором U+E007F. Для всего
  остального и для кластеров длиннее 32 `char` возвращает 0.
- **E2a.** Интеграция удаления: в `InputLogic.handleBackspaceEvent` в ветке без selection
  сначала вызывается `trailingEmojiClusterLength`; при результате > 0 выполняется ровно
  один `mConnection.deleteTextBeforeCursor(len)`, иначе прежний путь по кодпоинту без
  изменений. Ветка selection и ветка отката «двойной пробел → точка» не трогаются.
  `RichInputConnection.getUnicodeSteps` (свайп курсора и свайп-удаление) остаётся
  кодпоинтным и в E2 намеренно не чинится; расхождение двух реализаций шага по тексту
  записывается в docs как известный долг.
- **E2b-1. Клавиша, коды и поверхность — без содержимого панели.** `Constants.CODE_EMOJI =
  -14`; в `KeyboardCodesSet` добавляется СИНХРОННАЯ пара `"key_emoji"` /
  `Constants.CODE_EMOJI` сразу после `key_language_switch`, и в этом же изменении
  устраняется существующий рассинхрон массивов (17 имён `ID_TO_NAME` против 15 кодов
  `DEFAULT`, из-за которого `key_right` и `key_unspecified` дают
  `ArrayIndexOutOfBoundsException`) без смены кода ни у одного уже используемого в ресурсах
  имени. Добавляются `emojiKeyStyle`, свой VectorDrawable, сама клавиша в выбранный нижний
  ряд и новая ветка `case Constants.CODE_EMOJI` в `InputLogic.handleFunctionalEvent`,
  которая текст не меняет. В обоих `res/layout/input_view.xml` и
  `res/layout-v28/input_view.xml` появляется `ViewStub` `@id/emoji_panel_stub` внутри
  `@id/keyboard_stack` по образцу `suggestion_strip_stub`. Панель на этом шаге —
  намеренная заглушка: сплошной фон и две функциональные клавиши («АБВ» и удаление), без
  сетки, снапшота и прокрутки. Здесь же выполняется полное переключение поверхностей и все
  четыре зависимые точки: `KeyboardSwitcher.getVisibleKeyboardView()` возвращает активную
  поверхность; `getKeyboardSwitchState()` не возвращает `HIDDEN`, пока панель показана;
  `setMainKeyboardFrame()` не возвращает `MainKeyboardView` в `VISIBLE`, пока панель
  активна; `InputView.getVisibleInputBounds()` объединяет bounds панели тем же
  `outBounds.union(...)`, что и bounds полосы подсказок. Структура
  `LatinIME.onComputeInsets` не переписывается. Причина отдельной подфазы: это самая
  рискованная и самая легко пропускаемая часть E2, и она обязана проверяться на диффе, в
  котором больше ничего нет.
- **E2b-2. Содержимое панели.** `EmojiPanelState` — чистые геометрия и состояние (колонки,
  строки, `scrollY`, активная категория, hit-тест, нажатая ячейка, активный pointer) по
  образцу `SuggestionStripState`, полностью покрытые JVM-тестами без Android.
  `EmojiPanelController` — сериализованный владелец по образцу `SuggestionsController`:
  собственный single-thread executor и `UiPoster`, ровно одна подготовка снапшота за
  процесс (чтение asset + проба глифов + компоновка), состояния NOT_PREPARED / PREPARING /
  READY / UNAVAILABLE и один latest-only отложенный запрос «показать по готовности».
  Подготовка запускается только при первом нажатии клавиши эмодзи, никогда в `onCreate` и
  никогда на UI-потоке. `EmojiSurface`/`EmojiHost` — узкие интерфейсы в `LatinIME` по
  образцу `StripSurface`/`EditorSurface`. Вставка идёт исключительно существующим путём
  `LatinIME.onTextInput(String)` → `Event.createSoftwareTextEvent(rawText,
  CODE_OUTPUT_TEXT)` → `InputLogic.onTextInput`; своего пути вставки панель не заводит.
  Удаление внутри панели шлёт `Constants.CODE_DELETE` существующим путём
  `LatinIME.onCodeInput`, с автоповтором при удержании по `config_key_repeat_start_timeout`
  (400 мс) и `config_key_repeat_interval` (50 мс). Полоса подсказок при показе панели
  немедленно уходит в пустое состояние через идемпотентный
  `SuggestionsController.onSelectionChanged()`; её высота и видимость не меняются.
- **E2b-3. Прокрутка и «недавние».** Fling через один переиспользуемый `OverScroller`;
  `VelocityTracker` берётся не чаще одного раза на жест и освобождается на
  ACTION_UP/ACTION_CANCEL; рисуются только видимые строки сетки. «Недавние»: до 24 записей
  в порядке MRU, суммарно ≤ 512 символов, разделитель U+001F. **Хранение — файл в
  device-protected `noBackupFilesDir`, а не `SharedPreferences`**: домен `d_nb` исключён из
  резервного копирования по конструкции и не зависит от разбора XML-правил (в манифесте
  сейчас `allowBackup="true"` и `fullBackupOnly="true"` вообще без правил, а
  `SettingsHostActivity` вызывает `BackupManager.dataChanged()`). Дополнительно в E2
  вводятся `android:dataExtractionRules` (API 31+) и `android:fullBackupContent` (24–30),
  исключающие носитель «недавних» и в секции облачного бэкапа, и в секции переноса на новое
  устройство. Запись выполняется не чаще одного раза на скрытие панели и только при
  изменении списка. Гейт записи — `mShouldShowSuggestions == true` (это уже покрывает
  password, visible password, e-mail, URI, filter, `NO_SUGGESTIONS`, autocomplete), а не
  один лишь `mIsPasswordField`. При чтении отбрасываются записи, отсутствующие в текущем
  снапшоте; повреждённое значение даёт пустой список. Вкладка «Недавние» показывается
  первой и только когда список непуст. Отступление от сквозного правила: список не
  ключуется по subtype, потому что набор эмодзи языконезависим (объявлено явно в разделе
  «Сквозное решение»).
- **E2c.** `ExploreByTouchHelper` на панели по образцу `SuggestionStripView`: виртуальные
  ноды только для видимых ячеек, вкладок и двух функциональных клавиш; `contentDescription`
  ячейки — сама последовательность (собственная база названий эмодзи не поставляется);
  вкладки и функциональные клавиши получают строки en base / ru / tt; корневая нода
  экспонирует `ACTION_SCROLL_FORWARD`/`ACTION_SCROLL_BACKWARD`; `invalidateRoot()`
  вызывается при смене категории и по завершении прокрутки и не вызывается при выключенном
  touch exploration.
- **E2c.** Пересоздание input view (поворот, смена темы, смена высоты клавиатуры, смена
  subtype с перезагрузкой раскладки): панель закрывается, показывается буквенная
  клавиатура; ссылки сбрасываются в `KeyboardSwitcher.onCreateInputView()` и в
  `InputView.release()`/`onDetachedFromWindow()`. Состояние «панель была открыта» через
  пересоздание не переносится. Панель не аллокирует offscreen `Bitmap` вообще и
  освобождает свои кэши по `LatinIME.deallocateMemory()` (`MSG_DEALLOCATE_MEMORY`, 10 с) и
  по `onFinishInputView`.
- **E2c.** Раздел «Состояния полосы» дополняется ОДНОЙ новой строкой «Панель эмодзи
  показана»: полоса видима, 40dp, lookup не выполняется, ячейки пустые и inert. Ни одна
  существующая строка таблицы не меняется; правка вносится письменно в момент выполнения
  E2c.
- **E2c.** Privacy-тест нового пакета эмодзи по образцу `DictionaryStoragePrivacyTest`:
  нет `android.util.Log`, `println(`, `System.out`, `java.net.`, аналитики. Локализация всех
  новых строк (en base / ru / tt); вычитка татарских строк носителем языка — отдельный
  открытый пункт. Gates: полный JVM-набор, `lintVitalRelease`,
  `scripts/check-no-internet.sh` на debug и release artifact, записанная APK delta,
  allocation- и frame-тесты панели, device-UAT матрица на реальном Samsung/One UI.

### Fail-closed acceptance

- Одинаковый вход (`emoji-test.txt` закреплённой версии плюс версия `emoji_pack.py`) даёт
  байт-в-байт одинаковый `emoji_set_v1.txt`; подтверждается сравнением SHA-256.
- Превышение guardrail (> 65 536 Б или > 1 400 записей), дубликат, неизвестная категория,
  невалидный UTF-8 или несовпадение SHA-256 входа завершают `emoji_pack.py` ненулевым
  кодом; частично сгенерированный asset не появляется.
- Прирост release APK за всю E2 ≤ 40 960 Б к ИЗМЕРЕННОМУ артефакту после E1; вклад самого
  asset ≤ 16 384 Б; абсолютный размер ≤ 3 145 728 Б. Числа снимаются `stat` по unsigned
  release APK и записываются в docs вместе с остатком до hard limit.
- В APK нет ни одного файла `.ttf`/`.otf`, новых runtime-зависимостей и новых permission;
  `scripts/check-no-internet.sh` проходит и на source-манифесте, и на debug, и на release
  artifact.
- Ни одна ячейка не показывает последовательность, для которой `GlyphProbe.hasGlyph` вернул
  `false`. JVM: при фейковой пробе, отвергающей половину набора, снапшот содержит ровно
  доступные записи, сетка компактна и индексы ячеек не смещаются при прокрутке.
- Категория с 0 записей после фильтрации не показывает вкладку. Если доступных записей 0
  или подготовка снапшота провалилась, панель не показывается в этом процессе никогда,
  клавиша эмодзи ведёт себя как no-op (только тактильный отклик), обычный ввод полностью
  работоспособен.
- Пока снапшот не опубликован, нажатие клавиши ставит ровно один latest-only отложенный
  показ; он отбрасывается при любом другом нажатии, смене editor session,
  `onFinishInputView` или пересоздании input view. Двойное нажатие не ставит два запроса и
  не создаёт двух подготовок (JVM со счётчиком запусков).
- Одно нажатие удаления удаляет целиком каждый класс: одиночный BMP-эмодзи; суррогатную
  пару; последовательность с VS16; эмодзи с модификатором тона; ZWJ из двух и из трёх
  базовых эмодзи; keycap; пару региональных индикаторов; tag-последовательность.
- Для не-emoji текста число удалённых `char` за одно нажатие совпадает с поведением до E2:
  комбинирующая метка NFD, татарская и русская кириллица, латиница, цифра, пробел, пустой
  ввод, оборванная суррогатная пара (характеризационные JVM-тесты).
- Кластер длиннее 32 `char` даёт `trailingEmojiClusterLength == 0` и удаляется как один
  кодпоинт; текст не портится, исключений нет. При активном selection путь удаления не
  меняется вообще.
- **E2b-1:** пока панель показана, `outInsets.touchableRegion` покрывает её полностью —
  касания во всех четырёх углах, по каждой вкладке и по обеим функциональным клавишам
  обрабатываются клавиатурой и не проваливаются в приложение (device-UAT).
- **E2b-1:** `contentTopInsets` при открытой панели равен `contentTopInsets` при закрытой
  при том же состоянии полосы — разница 0 px (замер `dumpsys input_method`, как в D1f).
  Высота панели совпадает с высотой `MainKeyboardView` при настройке высоты 80%, 100% и
  150% и при ненулевом `pref_bottom_offset_portrait`.
- **E2b-1:** при подключённой физической клавиатуре и показанной панели
  `outInsets.touchableRegion` не очищается: `getKeyboardSwitchState()` не возвращает
  `HIDDEN`, `isImeSuppressedByHardwareKeyboard()` остаётся `false`, панель кликабельна.
- **E2b-1:** панель и `MainKeyboardView` никогда не видимы одновременно: любой
  `loadKeyboard`/`setKeyboard`/`setMainKeyboardFrame` во время показанной панели не делает
  `MainKeyboardView` видимым (UAT плюс source-contract тест на ветку видимости).
- **E2b-1:** поворот, смена высоты клавиатуры и смена темы при открытой панели закрывают
  панель, показывают буквенную клавиатуру, insets корректны, крэша и утечки View нет;
  повторное открытие после поворота работает.
- **E2b-1:** `KeyboardCodesSet.getCode("key_emoji")` возвращает `Constants.CODE_EMOJI`, а
  `getCode` для всех 11 имён, реально используемых в `res/xml`, возвращает те же коды, что
  до E2 (JVM-тест на весь массив имён). Клавиша эмодзи не появляется в раскладках символов,
  цифр и телефона.
- Существующий `SuggestionStripSourceContractTest` остаётся зелёным без правок: его
  ассерты подстрочные (`<ViewStub`, `@layout/suggestion_strip`,
  `android:layout_height="40dp"`, ровно одно вхождение `MainKeyboardView`), поэтому второй
  `ViewStub` их не нарушает. Причина зафиксирована в docs фазы: будущий stub с собственной
  высотой 40dp удовлетворил бы ассерт полосы молча.
- Тап по эмодзи выполняет ровно один `commitText` через `InputLogic.onTextInput`;
  source-contract подтверждает отсутствие собственного `commitText`/`deleteSurroundingText`
  в коде панели. После вставки полоса пуста, `mJustDoubleSpaced` сброшен, shift-состояние
  пересчитано существующим путём.
- Ни один замороженный контракт D1 не изменён: высота полосы 40dp, три ячейки, контракт
  префикса, регистра и автопробела дословно прежние; единственная правка таблицы состояний
  — добавленная строка «Панель эмодзи показана».
- **E2b-3:** allocation-тест — 0 аллокаций в `onDraw` и в обработке `ACTION_MOVE` за 200
  кадров непрерывной прокрутки. Source-contract запрещает в телах `onDraw`/`onTouchEvent`
  панели токены `= Rect(`, `= Paint(`, `MotionEvent.obtain`, `.toString()`, `TextUtils.`,
  `arrayOf(` (подстрока покрывает и `intArrayOf(`, и `charArrayOf(`), `listOf(`; список
  держится синхронным со списком существующего теста полосы.
- **E2b-3:** janky-кадры при непрерывной прокрутке ≤ 1% на реальном устройстве
  (программный рендерер эмулятора этот пункт не закрывает).
- Открытие панели при уже построенном снапшоте: от отпускания клавиши эмодзи до первого
  кадра панели p95 ≤ 100 мс на реальном устройстве. Метод замера записан в docs: 20
  скриптованных циклов открыть/закрыть, время кадра берётся из `gfxinfo`; при отсутствии
  инструментальной возможности критерий переформулируется как медиана плюс худший из 20 —
  но именно так и записывается, а не подменяется оценкой.
- Построение снапшота выполняется только на фоновом executor: source-contract подтверждает,
  что обращение к `AssetManager` и `Paint.hasGlyph` есть только в коде подготовки и
  отсутствует в `LatinIME.onCreate`, `onStartInputView`, `onDraw`, `onTouchEvent`.
  Холодный старт остаётся < 400 мс и не растёт относительно замера до E2.
- PSS: прирост при открытой панели относительно того же сценария без открытия ≤ 3,0 МБ
  (A/B в одном прогоне на реальном устройстве); абсолютный PSS не превышает потолок,
  установленный письменным решением владельца (см. блокирующий вход фазы), и записан.
  Возврат к исходному значению после `MSG_DEALLOCATE_MEMORY` **не является pass/fail
  критерием**: часть роста лежит в глиф-кэше системного шрифта, которым приложение не
  владеет. Вместо него проверяется то, что контролируется: по `MSG_DEALLOCATE_MEMORY`
  панель отпускает собственный снапшот и кэши раскладки и не держит offscreen `Bitmap`
  (JVM/source-contract плюс проверка ссылок), утечки View после закрытия панели нет, а
  наблюдённый PSS до и после записан как измерение.
- «Недавние» не записываются вообще в поле, где `mShouldShowSuggestions == false`
  (password, visible password, e-mail, URI, filter, `NO_SUGGESTIONS`, autocomplete):
  содержимое носителя после сессии ввода эмодзи в таком поле не меняется (JVM плюс
  проверка на устройстве). Тап по эмодзи не пишет на диск; запись выполняется не чаще
  одного раза на скрытие панели и только при изменении списка (JVM со счётчиком записей).
  Повреждённое или чужое значение даёт пустой список без исключения.
- Носитель «недавних» лежит в device-protected `noBackupFilesDir`, и правила бэкапа
  исключают его в обеих секциях (`cloud-backup` и `device-transfer`); проверяется
  source-contract тестом по `AndroidManifest.xml` и XML правил. Privacy-тест пакета эмодзи
  зелёный.
- TalkBack: отдельными кнопками объявляются только видимые ячейки, вкладки и две
  функциональные клавиши; невидимые ячейки нод не экспонируют; прокрутка выполняется
  действиями `ACTION_SCROLL_FORWARD`/`ACTION_SCROLL_BACKWARD`; активация ноды вставляет ту
  же последовательность, что и тап; при выключенном touch exploration панель не вызывает
  `announceForAccessibility` и `invalidateRoot()` при прокрутке.
- Gate каждой подфазы (E2a, E2b-1, E2b-2, E2b-3, E2c) выполняется отдельно; E2c
  дополнительно выполняет полный clean build и всю device-UAT матрицу и не заменяется
  накопленными быстрыми проверками.
- No-go: превышение дельты APK +40 960 Б или появление в APK файла шрифта, сетевой
  зависимости либо нового permission; показ хотя бы одной ячейки без глифа; backspace,
  оставляющий обломок эмодзи или изменивший поведение на не-emoji тексте; касание по
  видимой панели, уходящее в приложение; одновременная видимость панели и
  `MainKeyboardView` либо пустой `touchableRegion` при подключённой физической клавиатуре;
  аллокации в `onDraw`/`ACTION_MOVE` или janky-кадры > 1% на реальном устройстве; запись
  «недавних» в поле, где подсказки запрещены, или их попадание в резервную копию; чтение
  asset, проба глифов или любая подготовка на UI/cold-start пути; изменение любого
  замороженного контракта D1 сверх объявленной строки таблицы состояний; старт E2b-1 без
  письменного решения по PSS; поломка обычного ввода при любом отказе панели.

## E3 — устойчивость подсказок к опечаткам

Когда точный префикс даёт меньше трёх подсказок, оставшиеся ячейки заполняются словами,
отличающимися от набранного ровно на одно редактирование, ограниченное соседством клавиш
текущей раскладки: «китп» предлагает «китап», «мктәп» — «мәктәп», «телфон» — «телефон».
Точные подсказки не сдвигаются и не исчезают ни на одном префиксе, словарь не растёт ни на
байт. Подфазы: E3a (источник соседства и класс правок №1), E3b (классы №2 и №3), E3c
(классы №4 и №5, выпускается только по результатам замеров E3b).

Все числа полезности и стоимости ниже получены офлайн скриптами на Python, повторяющими
логику `TdictPrefixIndex` на реальном ассете `tatar_top100k_v1.tdict.zlib`, а не самой
Kotlin-реализацией. Они не факты о коде, а ориентиры, которые фаза обязана перепроверить.

### Scope и deliverable

- **E3a — источник соседства.** Карта строится из уже построенной раскладки:
  `Keyboard.getSortedKeys()` даёт код и x/y/width/height каждой клавиши,
  `Key.getMoreKeys()` (`MoreKeySpec.mCode`) даёт long-press пары а↔ә, о↔ө, у↔ү, ж↔җ, н↔ң,
  х↔һ, г↔һ, е↔ё, ь↔ъ. Отдельного XML-файла соседства не заводится: он дублировал бы
  раскладку и разошёлся бы с ней. Ни одна буква и ни одна пара в коде не хардкодится. Пары
  в данных односторонние и с дубликатами («ә» объявлена и на «а», и на «э», обратной
  ссылки у «ә» нет), поэтому симметризация и дедупликация выполняются явно — без них
  половина диакритических пар молча не заработает.
- **E3a — чистое ядро.** `KeyNeighborTable` строится чистой функцией из списка (кодпоинт,
  left/top/right/bottom, кодпоинты moreKeys) без единого Android-типа. Правило соседства:
  клавиши одного ряда, касающиеся по горизонтали, плюс клавиши соседнего ряда с
  горизонтальным перекрытием более 35% ширины более узкой из них; порог фиксируется в
  `docs/DICTIONARY-E3.md` как измеренная величина. На текущей татарской раскладке это даёт
  37 буквенных клавиш, средний fanout 3,51, максимум 5. Построение таблицы не логирует
  коды клавиш: это первый случай, когда данные раскладки пересекают границу пакета.
- **E3a — публикация таблицы.** `LatinIME` строит её там же, где пересчитывает
  `isTatarSuggestionsEligible()` (`onStartInputViewInternal`, `onCurrentSubtypeChanged`),
  кэширует по `KeyboardId` и отдаёт через `SuggestionsController` и новый метод
  `EngineHandle.updateKeyNeighbors(table)`. Таблица иммутабельна, несёт `subtypeId` и
  берётся только с алфавитного элемента (`KeyboardId.isAlphabetKeyboard()`): на shifted
  коды заглавные, на symbols — не буквы. Коды приводятся к NFC lowercase, некодпоинтные и
  небуквенные клавиши отбрасываются. Правило «брать только алфавитный элемент» — инженерная
  предосторожность, а не подтверждённый факт о поведении `getSortedKeys()`, и подтверждается
  тестом фазы.
- **E3a — subtype.** До D2 запрос по-прежнему несёт литерал
  `SuggestionsController.SUBTYPE_ID = "tt_RU"`, согласованный с таким же литералом в
  `LatinIME.isTatarSuggestionsEligible()`. Снятие литерала — работа D2, а не E3; после D2
  guard по несовпадению `subtypeId` таблицы и запроса перепроверяется отдельным тестом.
- **E3a — место поиска.** Нечёткий проход живёт внутри `TdictPrefixIndex`, потому что
  ранжирование требует частот, которых интерфейс `PrefixComputer` (возвращает
  `List<String>`) не отдаёт; сигнатура `PrefixComputer.lookup` не меняется. Генерация
  вариантов выносится в отдельный чистый `FuzzyPrefixVariants` и работает по кодпоинтам с
  повторным кодированием в UTF-8: побайтовая правка двухбайтовых кириллических букв даёт
  невалидный UTF-8 и молчаливый пустой результат.
- **E3a — класс редактирования №1:** замена буквы на её long-press партнёра в любой
  позиции. Офлайн-ориентир: p95 3 варианта, максимум 5; recovery@3 14,2% против базовых
  1,8%.
- **E3a — калибровка порогов.** JVM-тест фазы сначала воспроизводит офлайн-число recovery@3
  для класса №1 (14,2%) на том же воспроизводимом наборе опечаток в пределах согласованного
  допуска. Только после этого порог приёмки E3b считается действующим. Иначе корректная
  реализация может провалить gate из-за ошибки офлайн-модели, а не кода.
- **E3b — классы №2 и №3:** замена буквы на геометрического соседа и перестановка двух
  соседних букв. Совокупно с E3a офлайн-ориентир: p95 33 варианта (максимум 39), p95 133
  посещённые записи словаря (максимум 522), recovery@3 41,2%.
- **E3c — классы №4 и №5.** Класс №4 «лишняя буква» (удаление одного символа из набранного
  префикса; p95 39 вариантов, p95 332 записи, максимум 2931, recovery@3 52,6%) и класс №5
  «пропущенная буква» (вставка любой буквы алфавита раскладки в любую позицию; p95 328
  вариантов, recovery@3 56,8% при потолке 70,4%). Класс №5 — худшее соотношение пользы к
  цене во всём наборе: +4,2 п.п. за восьмикратный рост числа вариантов. Он выпускается
  только при подтверждённом запасе по времени на реальном устройстве и может не выйти
  вообще.
- **Ранжирование — новая редакция замороженного пункта.** Два уровня: сначала точные
  кандидаты в существующем порядке, затем неточные. Внутри каждого уровня прежнее правило —
  frequency descending, затем Unicode code-point lexical ascending. Исключение формы,
  равной набранному слову, действует на обоих уровнях. Приоритет по классу редактирования
  отвергнут по измерению: он поднимает мусор («киатров» выше «китап», «баллар» выше
  «балалар», «эшлекле» выше «эшләр»), тогда как чистая частота даёт правильный ответ.
  Редакция вносится в раздел «Контракт текста» письменно ДО кода. E4 позднее заменит её
  единой редакцией на три класса — это учтено в контракте E4, а не оставлено читателю.
- **Отсечения и бюджет.** Нечёткий проход не запускается вообще, если точный уровень уже
  дал три кандидата (87,5% реального ввода) или если длина префикса меньше 3 кодпоинтов;
  классы №4 и №5 дополнительно требуют длины не меньше 4. Расход ограничен детерминированным
  счётчиком (число вариантов и число посещённых записей) с фиксированными лимитами;
  превышение отбрасывает весь нечёткий уровень целиком, а не его часть. Второй рубеж —
  грубый предел по времени, который тоже может только отбросить уровень целиком; его
  срабатывание считается дефектом и проверяется тестом.
- **Свидетельства.** `docs/DICTIONARY-E3.md` (карта соседства, пороги, лимиты, latency, APK
  delta к измеренному артефакту после E2, число тестов на входе и выходе) и
  `docs/DICTIONARY-E3-TYPO-REVIEW.tsv` — воспроизводимый набор опечаток (генератор с
  фиксированным seed в `scripts/`) плюс человеческая классификация всех новых кандидатов на
  22 реальных префиксах из `docs/DICTIONARY-D1A-QUERY-REVIEW.tsv`.
- **Вне объёма:** новый пользовательский тумблер, визуальное различение неточных
  кандидатов, автозамена, изменение словарного ассета, изменение формата `.tdict`,
  изменение полосы подсказок и пути коммита.

### Fail-closed acceptance

- Префиксное подмножество: для всех 22 префиксов `docs/DICTIONARY-D1A-QUERY-REVIEW.tsv` и
  не менее чем для 10 000 случайных префиксов реального словаря результат E3 начинается
  ровно с результата D1 — те же строки в том же порядке; ни один точный кандидат не смещён,
  не заменён и не удалён.
- Неточные кандидаты появляются только в ячейках, пустых в D1. При трёх точных кандидатах
  нечёткий проход не выполняется — подтверждается счётчиком обращений к генератору
  вариантов, а не только совпадением результата.
- Порядок уровней: тест, в котором неточный кандидат имеет частоту выше любого точного,
  подтверждает, что он всё равно идёт после всех точных; внутри каждого уровня подтверждены
  frequency-desc и code-point-lexical tie-break.
- Дедупликация и exact-word exclusion: форма, в точности равная набранному нормализованному
  слову, отсутствует на обоих уровнях (отдельный тест на класс «лишняя буква» — единственный,
  способный её вернуть); одно и то же слово не занимает две ячейки.
- Контракт регистра не изменён: MIXED даёт 0 результатов до обращения к движку; неточные
  кандидаты получают регистр из `pendingPrefix` тем же `applyCasing` после ранжирования;
  сквозные тесты LOWER / INITIAL_CAPS / ALL_CAPS с неточными кандидатами зелёные,
  показанная и вставленная формы совпадают.
- Раскладка остаётся данными: source-contract тест подтверждает отсутствие кириллических
  литералов и захардкоженных пар клавиш в новых исходниках; таблица, построенная из реальной
  татарской раскладки, содержит все шесть букв пятого ряда и все long-press пары,
  объявленные в `rowkeys_tatar*.xml`.
- Таблица иммутабельна и привязана к subtype: при несовпадении `subtypeId` запроса и
  таблицы, при отсутствующей, пустой или неалфавитной таблице нечёткий проход не
  выполняется, а результат байт-в-байт равен результату D1.
- Детерминизм: 1000 повторов одного и того же префикса при неизменных словаре и таблице
  дают идентичный список.
- Бюджет расхода: тест с искусственно заниженным лимитом доказывает, что превышение
  отбрасывает весь нечёткий уровень и возвращает ровно точный результат; на всём
  наборе-опечаточнике лимит не срабатывает ни разу, предел по времени не срабатывает ни
  разу.
- Время: на реалистичной смеси префиксов compute p95 не хуже D1 более чем на 10%; на
  наборе, где нечёткий проход выполняется в 100% случаев, compute p95 ≤ 5 мс; худший
  единичный lookup в том же прогоне не превышает уже отгруженного худшего случая —
  однобуквенного префикса «к» (14 115 записей блока, тест
  `realMaximumOneLetterKFanoutComputeP95IsAtMostFiveMilliseconds`); request→publish p95
  ≤ 16 мс сохраняется; показанных stale results — 0.
- Качество: JVM-тест воспроизводит офлайн-recovery@3 класса №1 в пределах согласованного
  допуска; после этого recovery@3 на воспроизводимом наборе опечаток не ниже 35% после E3b
  и не ниже 50% после включения класса «лишняя буква», при измеренном базовом уровне D1
  1,8%. Набор, seed и числа зафиксированы в `docs/`.
- Шум: все новые (неточные) кандидаты, появляющиеся на 22 реальных корректно набранных
  префиксах, выписаны в `docs/DICTIONARY-E3-TYPO-REVIEW.tsv` и классифицированы человеком;
  строк с классификацией fail — ноль.
- Аллокации: на один вариант не создаётся ни `ImmutableUtf8Prefix`, ни `String`, ни
  коллекция; тест подтверждает, что число аллокаций на lookup не зависит от числа
  сгенерированных вариантов.
- Словарь и артефакт: SHA-256 `assets/dictionaries/tatar_top100k_v1.tdict.zlib` совпадает с
  v1.2.0 байт в байт; APK растёт не более чем на 15 360 Б к измеренному артефакту после E2
  при абсолютном пределе 3 145 728 Б; новых ассетов, новых mmap-регионов и новых файлов в
  device-protected storage нет.
- Неизменность соседних контрактов: `SuggestionStripView.kt`, `SuggestionStripState.kt`,
  `InputLogic.commitChosenSuggestion` и таблица состояний полосы не изменены; набор тестов,
  зафиксированный на входе фазы, проходит без ослабления ожиданий, новые только добавляются.
- Privacy: `DictionaryEnginePrivacyTest` остаётся зелёным; геометрия клавиш передаётся в
  движок только числами; ни одна введённая буква и ни один код клавиши не логируется.
- Отказоустойчивость: аппаратная клавиатура, ещё не построенный input view,
  symbols-раскладка, поворот во время активного запроса и повреждённая таблица дают
  поведение ровно уровня D1; обычный ввод при любом из этих условий полностью
  работоспособен.
- Каждая подфаза E3a/E3b/E3c проходит общий per-phase gate; редакция пункта ранжирования
  внесена в «Контракт текста» до кода E3a.
- No-go: изменение состава или порядка точных кандидатов хотя бы для одного префикса;
  неточный кандидат выше точного; недетерминированный результат при неизменных словаре и
  таблице; рост compute p95 на реалистичной смеси более чем на 10% или превышение 5 мс на
  наборе-опечаточнике; захардкоженная в коде раскладка, буква или пара клавиш; любое
  изменение словарного ассета или рост APK более 15 360 Б; правка контракта регистра,
  таблицы состояний полосы или пути коммита; порча пользовательского текста или
  неработоспособность обычного ввода при любом отказе нечёткого прохода.

## E4 — личный словарь, привязанный к активному subtype

Пользователь получает личный словарь: имена, названия деревень, заимствования и сленг,
которых в Leipzig нет и не будет, начинают предлагаться в той же полосе наравне со
словарными формами — офлайн, отдельно для каждого subtype, opt-in с default OFF. На экране
«Личный словарь» видно каждое запомненное слово, можно добавить слово вручную, удалить одно
слово и стереть всё. Подфазы: E4a-1 (формат и чтение), E4a-2 (запись и устойчивость), E4b
(настройка, слияние, экран управления), E4c (обучение), E4d (забыть слово долгим нажатием).
Порядок обязателен. План отхода при нехватке сил: сначала исключается E4d, затем E4c —
E4a+E4b дают работающий личный словарь с ручным добавлением.

**Блокирующие входы фазы:** принятая человеком единая редакция пункта ранжирования (ниже) и
раздел «Контракт личного словаря» в «Контракте текста»; выполненная E3 вместе с её
редакцией ранжирования — E4 заменяет её текст, а не пишет параллельный; выполненная D2,
владеющая рефакторингом «boolean eligible → идентификатор активного subtype», потребителем
которого E4 является.

### Scope и deliverable

- Новый код — Kotlin в новом пакете `latin/dictionary/personal/`. Java-база не
  конвертируется, новых зависимостей и NDK/JNI нет. Переиспользуются инфраструктурные швы:
  `DeviceProtectedDirectoryProvider`, `DurableFileOps`/`AndroidDurableFileOps`, `SpaceProbe`,
  `StorageClock`, семантика `PreparationResult`/`StorageFailure` и паттерн temp → fsync →
  atomic rename → fsync каталога.
- Всё привязано к идентификатору subtype с самого начала: путь на диске, имя файла,
  subtypeTag внутри файла, счётчики, снапшот в памяти и алфавитный фильтр параметризованы
  `Subtype.getLocale()`. Общего «дефолтного» хранилища нет; для subtype без объявленного
  алфавита фича выключена целиком.
- **E4a-1. Формат и чтение.** Новый формат `.tpers`, а НЕ `.tdict`, с письменным
  обоснованием в `docs/DICTIONARY-E4.md`: `DictionaryArtifactSpec` требует знать sha256 и
  entryCount до сборки, имя шьётся шаблоном `tatar_top100k-…`, retention 2/1, а активация
  через lease возвращает null, пока жив чужой reader — этот store спроектирован под
  неизменяемый asset и для файла, меняющегося в течение сессии, непригоден. Layout:
  фиксированный заголовок (magic `TATPERS\0`, schemaId u16 = 1, formatVersion u16 = 1,
  headerSize u16, checksumAlgorithm u16 = 1, entryCount u32, payloadSize u32, subtypeTag 16
  байт ASCII с нулевым паддингом, SHA-256 32 байта по всему файлу с занулённым полем
  контрольной суммы — та же конвенция, что `TdictValidator.calculateDigests`), затем записи
  в строгом порядке UTF-8 code-point ascending: длина слова в байтах u8, счётчик
  использования u16, серийник последнего использования u32, UTF-8 слово. `TpersValidator`
  по образцу `TdictValidator`, fail-closed при открытии: magic, schemaId, formatVersion,
  headerSize, checksumAlgorithm, совпадение subtypeTag с запрошенным subtype, entryCount ≤
  предела, payloadSize == факту, SHA-256, строгий UTF-8 (`CodingErrorAction.REPORT`), NFC
  lowercase, все кодпоинты в алфавите subtype, длина 3..24 кодпоинта, строгая сортировка без
  дубликатов, счётчик ≥ 1. Подфаза заканчивается read-only путём и полным набором тестов на
  повреждение; писателя в ней нет — формат замораживается до того, как на нём строится
  машинерия долговечности.
- **E4a-2. Запись и устойчивость.** Только целиком: эксклюзивный temp в том же каталоге →
  запись → flush → fsync файла → повторная валидация записанного → атомарная замена → fsync
  каталога; temp-мусор удаляется при открытии. `DurableFileOps` расширяется методом
  `atomicReplace(source, destination)`, потому что существующий `atomicRename` намеренно
  бросает при существующем destination и его семантику менять нельзя; `AndroidDurableFileOps`
  перестаёт быть `private object` и становится `internal`, чтобы логика fsync/rename не
  дублировалась; семантика D1b при этом не меняется. Размещение: `personal/` внутри
  device-protected `noBackupFilesDir` (домен `d_nb` исключён из резервного копирования по
  конструкции), файлы `personal-<subtypeTag>-s1-f1.tpers`, счётчики
  `pending-<subtypeTag>-s1-f1.bin`, соль `salt.bin`, temp `.personal-<…>.tmp`. Каталог
  `dictionaries/` не затрагивается, чтобы процессная lease-координация D1b не касалась
  личных файлов. Один процессный владелец на каталог с собственным lock:
  `SettingsHostActivity` объявлен без `android:process`, то есть экран настроек и IME живут
  в одном процессе. Все мутации — сериализованные события на единственном фоновом executor:
  `noteCompletion(word)`, `learn(word)`, `addManually(word)`, `forget(word)`, `clearAll()`;
  UI-поток не выполняет ни I/O, ни checksum, ни запись, ни чтение файла. После каждой
  успешной мутации собирается новый ИММУТАБЕЛЬНЫЙ снапшот (отсортированный `Array<String>`
  плюс параллельный `IntArray` счётчиков) и публикуется через `@Volatile`-ссылку; изменение
  структуры на месте запрещено, снапшот читается с worker-потока движка. Пределы:
  MAX_PERSONAL_ENTRIES = 2 000 слов на subtype, файл ≤ 128 КБ, MAX_PENDING = 256 записей на
  subtype; при переполнении вытесняется запись с минимальным серийником последнего
  использования (LRU по монотонному файловому серийнику, без зависимости от системных
  часов).
- **E4a-2. Резервное копирование — защита в глубину.** Помимо `noBackupFilesDir`,
  добавляются `android:dataExtractionRules` (API 31+) и `android:fullBackupContent` (24–30);
  правила исключают `personal/`, производный `dictionaries/`, носитель «недавних» эмодзи и
  ключ «предложение израсходовано» И в секции облачного бэкапа, И в секции переноса на новое
  устройство. Это условие fail-closed: оно не зависит от того, попадает ли device-protected
  storage в Auto Backup по умолчанию, и от того, как легаси-формат `fullBackupContent`
  разбирает домен `device_file` на API 24–30. Сейчас в манифесте объявлены
  `allowBackup="true"` и `fullBackupOnly="true"` без каких-либо правил, а
  `SettingsHostActivity` вызывает `BackupManager.dataChanged()`.
- **E4a-2. Privacy-гейт нового пакета** по образцу `DictionaryStoragePrivacyTest`: нет
  `android.util.Log`, `println(`, `System.out`, `java.net.`, аналитики, нет
  `createCredentialProtectedStorageContext()`; публичная поверхность не принимает и не
  возвращает набранный текст в именах методов. Существующий тест сканирует только каталог
  `storage`, поэтому новому пакету нужен свой аналог.
- **E4b. Настройка.** `PREF_PERSONAL_DICTIONARY`, default OFF: ключ рядом с
  `PREF_TATAR_SUGGESTIONS`, reader рядом с `readTatarSuggestionsEnabled`, поле в
  `SettingsValues`, строка в `SettingsHostActivity.buildPreferencesScreen`. Строка выключена
  (`setRowEnabled(false)`), когда `PREF_TATAR_SUGGESTIONS` = false. Текст настройки прямо
  говорит, что набранные слова сохраняются на устройстве и что выключение тумблера
  накопленное НЕ удаляет — стереть можно на экране «Личный словарь». Ключ добавляется в
  `res/xml/app_restrictions.xml` и в whitelist `Settings.loadRestrictions`: политика «не
  запоминать» на управляемом устройстве обязана быть выразимой, иначе закрытый
  switch-whitelist делает её невозможной.
- **E4b. Единая редакция пункта ранжирования — заменяет редакцию E3 целиком.** Полный
  порядок кандидатов: (1) точные словарные кандидаты в существующем порядке — frequency
  descending, затем Unicode code-point lexical ascending; (2) не более ОДНОГО personal-only
  слова (личный порядок: usage count desc, затем code-point asc) — индекс 0, если точных
  словарных кандидатов нет, иначе индекс 1; (3) неточные (fuzzy) словарные кандидаты E3 в
  порядке своего уровня. Дубликат по нормализованной форме считается словарным и
  показывается один раз. Исключение формы, равной набранному слову, действует на всех трёх
  классах. **Отменяемые утверждения приёмки E3 и их новые формулировки:** вместо «результат
  начинается ровно с результата D1 — те же строки в том же порядке» действует «при
  выключенном личном словаре результат байт-в-байт равен результату E3, а при включённом
  точные словарные кандидаты сохраняют относительный порядок между собой и могут быть
  сдвинуты вниз ровно одним personal-only словом»; вместо «неточные кандидаты появляются
  только в ячейках, пустых в D1» действует «неточные кандидаты появляются только после всех
  точных и после personal-only».
- **E4b. Реализуемость слияния.** Слой слияния обязан различать класс кандидата, поэтому
  слияние с личным источником выполняется в ТОМ ЖЕ вычислителе, где живёт нечёткий проход
  E3 (там есть и частоты, и метка класса), а наружу через `PrefixComputer.lookup`
  по-прежнему уходит `List<String>`. `CompositePrefixComputer(primary, personal)`
  подставляется в `MappedDictionaryEngine.startOwnedLease` — правка внутренняя, функция
  приватная, публичная поверхность движка не расширяется. Второй `request()`, второй
  `LookupToken` и изменение семантики `isCurrent` запрещены: latest-only модель остаётся
  нетронутой.
- **E4b. Что не меняется:** границы слова, контракт регистра (MIXED → 0 результатов),
  таблица состояний полосы (три ячейки, 40dp), privacy-гейты, автопробел и единственный путь
  вставки `InputLogic.commitChosenSuggestion` — личные кандидаты идут через него без
  исключений.
- **E4b. Смена subtype.** Фактическая смена идентификатора немедленно закрывает eligibility
  (полоса `GONE`, generation инвалидирована, displayed candidates отвязаны, новых lookup
  нет), а блокирующие `releaseEngine` + `start` выполняются на следующей границе
  `onFinishInputView`/`onStartInput` механизмом отложенного освобождения E1a-7. Блокировать
  UI-поток в `onCurrentSubtypeChanged()` запрещено: `destroyHandle` стоит до 60 мс и при
  неудаче ещё до 180 мс, то есть до 240 мс на нажатие глобуса, и source-contract тест E1a
  это запрещает. Возврат в тот же subtype (tt→ru→tt) идентификатор не меняет, поэтому
  warm-engine re-request D1e сохраняется.
- **E4b. Экран «Личный словарь»** в `SettingsHostActivity`: новый
  `Screen.PERSONAL_DICTIONARY`, вход `linkRow` с экрана Preferences; секция на язык, строка
  на каждое запомненное слово с действием «Удалить», `actionRow` «Добавить слово…» (диалог с
  полем ввода и тем же фильтром валидации, что при обучении) и `actionRow` «Стереть всё» с
  подтверждающим диалогом. Экран полностью работоспособен и при выключенной настройке —
  стереть накопленное должно быть можно всегда. Экран получает `FLAG_SECURE`: это список
  того, что человек печатал, и без флага он попадает в миниатюру «недавних приложений» и
  снимается скриншотом. `SettingsHostActivity` уже объявлен `exported="false"`, поэтому из
  чужих приложений экран недостижим.
- **E4b. Политика конфиденциальности.** `PRIVACY.md` правится на обоих языках с повышением
  версии ДО первой записи пользовательского текста: что именно записывается (нормализованные
  слова, трижды завершённые чисто, плюс солёные усечённые хеши счётчиков), куда
  (device-protected storage приложения, отдельно на каждый subtype), что это никогда не
  покидает устройство, что это исключено из облачного бэкапа и переноса на новое устройство,
  что фича opt-in с default OFF и как стереть всё накопленное. Сверяются и при необходимости
  правятся `README.md` и `metadata/en-US/full_description.txt`. Причина: действующая версия
  1.0 утверждает дословно «does not collect, store, or transmit any data. Period.», и E4 —
  первая фаза, которая пишет на диск именно напечатанное.
- **E4b. Строки** en (`values`), ru (`values-ru`), tt (`values-tt`); татарские помечаются
  как требующие вычитки носителем языка.
- **E4c. Событие «слово завершено»** вычисляется в `SuggestionsController` по существующим
  хукам (`onTextChanged`, `onSelectionChanged`, `onFinishInput`, `onTap`,
  `onSuggestionsAffectingCursorMove`) без нового IPC: чистый пробег = слово росло по одному
  символу (`w.startsWith(lastWord) && w.length > lastWord.length`) и завершилось переходом
  trailing word в пустую строку. Backspace или любое сокращение, смена selection, внутренний
  жест курсора, смена subtype/поля и принятая подсказка помечают пробег грязным.
- **E4c. Фильтр «слова нет в основном словаре»** без новых API движка и без доступа к mmap
  с UI-потока: слово W считается неизвестным только если для какого-то его собственного
  префикса p (|p| < |W|), фактически запрошенного в этом же чистом пробеге, `applyResult`
  получил ПУСТОЙ список. Пустой результат для p означает, что ни одно словарное слово, кроме
  самого p, не начинается с p, следовательно W ∉ словарь. Если такого наблюдения не было
  (например запросы схлопнул coalescing), слово не запоминается — fail-closed в сторону
  меньшей записи.
- **E4c. Порог** LEARN_THRESHOLD = 3 чистых завершения, счёт отдельный на subtype.
  Обоснование: 1 запоминает любую опечатку; 2 запоминает повторённую опечатку — одну и ту же
  ошибку человек делает подряд; 3 требует, чтобы форма выжила три независимых завершения без
  единого исправления. Порог также ограничивает срок жизни pending-записей.
- **E4c. Гейт «не персонализироваться».** В `InputAttributes` вводится финальное поле
  `mNoPersonalizedLearning`, читаемое как
  `0 != (editorInfo.imeOptions & EditorInfo.IME_FLAG_NO_PERSONALIZED_LEARNING)` и
  вычисляемое ДО early-return для не-TEXT классов; при `editorInfo == null` — истина
  (fail-closed). Условие обучения: `isTatarSuggestionsEligible()` И настройка ON И
  `!mNoPersonalizedLearning`. Запрет распространяется на `noteCompletion`, `learn` и запись
  pending-счётчиков, а не только на публикацию в основной файл. Это стандартный сигнал
  Android, которым банковские приложения, менеджеры паролей и инкогнито-режимы браузеров
  просят IME не запоминать; сейчас флаг не встречается в проекте ни разу. Показ подсказок из
  уже накопленного словаря при этом флаге остаётся разрешён (это чтение, а не сбор), и это
  решение фиксируется письменно в `docs/DICTIONARY-E4.md`.
- **E4c. Pending-счётчики не хранят текст:** ключ — первые 8 байт SHA-256(salt ‖ NFC
  lowercase слово), значение — счётчик u16 и серийник u32; соль 16 случайных байт в
  `salt.bin`, пересоздаётся после «стереть всё». В `docs/DICTIONARY-E4.md` прямо
  фиксируется, что это защита от случайного извлечения файла, а не от атакующего, у которого
  есть и файл, и соль. Частота записи: pending держатся в памяти и сбрасываются на диск не
  чаще одного раза на `onFinishInput`/границу lifecycle и только при изменении — не на
  каждое завершённое слово.
- **E4c. Контентные фильтры** (на нормализованной NFC lowercase форме, одинаково для pending
  и для основного файла): все кодпоинты входят в алфавит активного subtype (это отсекает
  цифры, латиницу, e-mail, URL, `@`, точки, дефисы, апострофы и любые коды); длина 3..24
  кодпоинта; регистр сырого слова ≠ MIXED; после NFC не остаётся комбинирующих меток.
  Алфавит по subtype задаётся одной таблицей данных в одном месте; JVM-тест пиннит tt_RU к
  тому же набору кодпоинтов, что `TdictValidator.TATAR_ALPHABET`.
- **E4c. Privacy-скан расширяется на `latin/suggestions/`** по образцу
  `DictionaryEnginePrivacyTest`: запрещены `android.util.Log`, `println(`, `System.out`,
  `java.net.`, аналитика и передача слова в конкатенацию логгера. Именно в этом пакете живёт
  детекция завершённого слова, а сегодня privacy-гейта у него нет вообще; `Log` там сейчас
  отсутствует, то есть гейт ставится бесплатно и работает как защита от регресса.
- **E4d. Долгое нажатие** по ячейке, показывающей слово из личного словаря, открывает диалог
  «Забыть „X“?» поверх окна IME (привязка окна — образец `RichInputMethodManager.
  showSubtypePicker`, хранение и гашение — `LatinIME.mOptionsDialog` и `hideWindow`);
  подтверждение удаляет слово и его pending-хеш. Долгое нажатие по словарному слову не делает
  ничего. Принадлежность определяется бинарным поиском по опубликованному снапшоту, поэтому
  `LookupResult` не расширяется. Срабатывание таймера отменяет tap этой последовательности
  касаний — долгое нажатие НИКОГДА не коммитит текст. Таймер — одно заранее созданное
  поле-`Runnable` плюс `postDelayed`/`removeCallbacks`; в телах `onDraw`/`onTouchEvent` не
  появляется ни одной аллокации. Виртуальной ячейке добавляется `ACTION_LONG_CLICK` только
  для личных слов.
- **E4d. Явное «запомнить»** реализуется НЕ жестом по полосе, а строкой «Добавить слово…» на
  экране «Личный словарь»: набранного слова в полосе нет по frozen-контракту (exact-word
  exclusion), а показ его отдельной ячейкой сломал бы и таблицу состояний, и правило
  исключения.
- **Deliverable-документы:** `docs/DICTIONARY-E4.md` (формат, обоснование выбора формата,
  свидетельства тестов и замеров, честные оговорки) и правки «Контракта текста» — единая
  редакция ранжирования и раздел «Контракт личного словаря».
- **Вне объёма E4:** подъём личного слова на позицию 0, предпочитаемый регистр личных имён,
  биграммы и предсказание следующего слова (E5), автозамена (D3), исключения по приложениям,
  экспорт/импорт и любая синхронизация.

### Fail-closed acceptance

- При `PREF_PERSONAL_DICTIONARY = false` в каталоге `personal/` не создаётся ни одного
  файла: JVM-тест на store плюс проверка на устройстве после сессии ввода не менее 50 слов.
- В поле пароля и в любом поле с `mShouldShowSuggestions == false` не создаётся и не
  изменяется ни одна запись и ни один pending-хеш: по одному детерминированному тесту на
  password, visible password, e-mail, URI, filter, `NO_SUGGESTIONS`, autocomplete.
- В поле с `IME_FLAG_NO_PERSONALIZED_LEARNING` после трёх чистых завершений нет ни одной
  записи в `.tpers` и ни одного pending-хеша; при `editorInfo == null` поведение то же.
- Ни один байт файла pending-счётчиков не равен UTF-8 представлению набранного слова: тест
  печатает контрольное слово, читает файл и ищет подстроку — совпадений 0. Число физических
  записей pending за сессию из N завершённых слов не растёт с N (счётчик записей в тесте).
- Слово, содержащее кодпоинт вне алфавита subtype, цифру, латиницу, `@`, точку или дефис, не
  попадает ни в pending, ни в основной файл: по одному тесту на класс входа, включая
  `guzel@mail.ru`, `t.me/abc`, `код1234`, `iPhone`, `ГҮЗӘЛ2`.
- `personal/` лежит в device-protected `noBackupFilesDir`; манифест ссылается на правила
  извлечения данных, и правила исключают `personal/`, `dictionaries/`, носитель «недавних»
  эмодзи и ключ онбординга в обеих секциях (облачный бэкап и перенос на устройство);
  проверяется source-contract тестом по `AndroidManifest.xml` и XML правил.
- `PRIVACY.md` содержит раздел о личном словаре, его версия не равна 1.0, и утверждение
  «не хранит никакие данные» в нём отсутствует; `README.md` и `metadata/` сверены.
- Разрешения `INTERNET` нет, сетевых вызовов и аналитики в новом пакете нет: no-INTERNET
  gate на собранном artifact пройден, privacy-тест пакета `personal` зелёный, privacy-скан
  пакета `latin/suggestions/` зелёный.
- «Стереть всё» удаляет файлы всех языков, pending-файлы и соль, каталог `personal/` после
  этого не содержит ни одного файла (fsync каталога выполнен), а работающий engine на
  следующем lookup не возвращает ни одного личного кандидата без перезапуска IME.
  Заявляется именно это, а НЕ физическое затирание флеш-памяти.
- Удаление одного слова убирает его и из файла, и из pending; следующий lookup по его
  префиксу его не показывает. Слово, добавленное вручную, предлагается по своему префиксу в
  уже открытом поле без перезапуска клавиатуры.
- Слово, трижды завершённое чисто, предлагается; после двух завершений — не предлагается.
  Завершение с backspace внутри слова, со сменой selection, с внутренним жестом курсора или
  с принятой подсказкой не увеличивает счётчик: по одному тесту на каждый случай.
- Порядок кандидатов соответствует единой редакции: при наличии точных словарных кандидатов
  personal-only слово занимает индекс 1 и не более одной ячейки; при их отсутствии — индекс
  0; неточные кандидаты E3 идут после всех точных и после personal-only; при выключенном
  личном словаре результат байт-в-байт равен результату E3. Полоса остаётся ровно тремя
  ячейками и 40dp.
- Слово, присутствующее и в словаре, и в личном списке, показывается ровно один раз. Форма,
  в точности равная набранному нормализованному слову, не показывается и из личного словаря.
- MIXED-регистр даёт 0 результатов без обращения к движку; Initial Caps и ALL CAPS
  применяются к личным кандидатам тем же `applyCasing` и только после ранжирования;
  показанная и вставленная формы совпадают.
- Личные слова татарского subtype не появляются ни в одном другом subtype: тест на паре
  (tt_RU, ru_RU) с одинаковым префиксом. При фактической смене идентификатора движок
  пересоздаётся на границе lifecycle, а не в `onCurrentSubtypeChanged`; при возврате
  tt→ru→tt не пересоздаётся и существующий тест
  `subtypeChangeToEligibleWithWarmEngineReRequestsCurrentPrefix` остаётся зелёным.
  Source-contract тест E1a («блокирующее освобождение только из
  `onFinishInputView`/`onStartInput`») остаётся зелёным без правок.
- Оборванная запись: при сбое между temp и заменой доступен прежний валидный файл либо, для
  первой записи, никакой; partial никогда не становится основным. Тест с инъекцией сбоя на
  каждом шаге write/fsync/validate/replace/fsync-dir.
- Повреждение: испорченный байт в любой секции (magic, schema, formatVersion, subtypeTag,
  checksum, порядок, длина, невалидный UTF-8, слово вне алфавита) приводит к удалению файла,
  пустому личному словарю, продолжающим работать обычным подсказкам и обычному вводу, без
  крэша. По одному тесту на вид повреждения.
- Нехватка места: отказ `SpaceProbe`/ENOSPC отбрасывает изменение, прежний файл остаётся
  целым, фича продолжает работать в режиме чтения, temp-мусор не остаётся.
- Переполнение: при 2 000 записях новое слово вытесняет запись с минимальным серийником
  последнего использования; файл ≤ 128 КБ; pending ≤ 256 записей.
- Direct boot: после перезагрузки без разблокировки личные подсказки читаются и работают, из
  поля разблокировки ничего не запоминается, крэша нет.
- Обновление приложения: файл с тем же schemaId/formatVersion читается без потери слов; файл
  с другими — не читается, удаляется, личный словарь пуст, ввод не ломается.
- Экран настроек и IME в одном процессе не конфликтуют: удаление слова из настроек при
  открытой клавиатуре не приводит ни к потере файла, ни к рассинхрону снапшота.
- Ни одной блокирующей операции на UI-потоке: I/O, checksum, чтение и запись `.tpers`
  выполняются только на фоновом executor (source-contract плюс отсутствие ANR в device-UAT).
- Бюджеты latency при 2 000 личных записей: prefix lookup compute p95 ≤ 5 мс, полный
  request→publish warm p95 ≤ 16 мс, показанных stale results — 0. Отдельный пункт на
  совмещённый случай: нечёткий проход E3 плюс личный источник в ОДНОМ lookup укладываются в
  те же 5 мс и 16 мс.
- Прирост APK ≤ 25 600 Б к измеренному артефакту непосредственно перед E4 (его размер и
  SHA-256 записаны в `docs/DICTIONARY-E4.md` в начале фазы, а не взяты из прогноза);
  абсолютный размер ≤ 3 145 728 Б; delta и остаток до hard limit записаны.
- Дельта PSS от включённого личного словаря с 2 000 записями ≤ 0,5 МБ относительно того же
  артефакта с выключенной настройкой (чистый A/B на одном устройстве). Абсолютный потолок
  действует в редакции письменного решения владельца по PSS.
- Ноль аллокаций в hot draw/touch сохраняется, janky-кадры ≤ 1% — для E4d замер выполняется
  с включённым таймером долгого нажатия. Долгое нажатие не коммитит текст ни в одном
  сценарии.
- Набор тестов, зафиксированный на входе фазы, зелёный без ослабления ожиданий; осознанно
  обновляются только пиннинги source-contract тестов, и каждое обновление объяснено;
  `lintVitalRelease` BUILD SUCCESSFUL; no-INTERNET gate на собранном artifact пройден.
- Единая редакция ранжирования и раздел «Контракт личного словаря» внесены в «Контракт
  текста» и приняты человеком ДО кода E4b; в тексте контракта не осталось редакции E3 в
  противоречии с новой.
- No-go: любая запись пользовательского текста при выключенной настройке, в
  password/`NO_SUGGESTIONS`-поле, при `IME_FLAG_NO_PERSONALIZED_LEARNING` или вне алфавита
  активного subtype; личные слова, всплывающие в чужом subtype; «стереть всё», оставившее
  файл, pending-хеш, соль или живой снапшот в памяти; порча пользовательского текста или
  неработающий обычный ввод при повреждении, переполнении, нехватке места или direct boot;
  partial-файл, ставший основным; правила backup/device-transfer, не исключающие `personal/`;
  блокирующее освобождение движка в `onCurrentSubtypeChanged`; выход за бюджеты
  compute/PSS/APK; закрытие фазы при неизменённой `PRIVACY.md`; расхождение кода с
  «Контрактом текста» или ослабление существующих тестов вместо осознанного обновления
  контракта.

## E5 — предсказание следующего слова (биграммы) с ранним гейтом по размеру

После принятого или набранного слова и пробела полоса вместо пустой показывает до трёх
вероятных продолжений на основе предыдущего слова; тап вставляет слово с автопробелом, не
удаляя ни одного символа пользовательского текста. Объём определяется измерением: сначала
прототипом измеряются размер и полезность таблицы биграмм, и только после прохождения гейта
пишется Android-код. Подфазы: E5a (измерение и гейт, Android-код не меняется), E5b (формат,
генератор, asset, хранилище), E5c (движок предсказаний), E5d (интеграция, настройка,
контракт, UAT).

**Блокирующие входы:** согласованный человеком числовой порог полезности ДО запуска E5a
(иначе гейт превратится в подгонку под результат); загруженные человеком корпуса (у агентов
сети нет); D2 как владелец привязки к активному subtype; корректный перезамер PSS на
реальном железе — он блокирует E5d, но не E5a.

### Scope и deliverable

- **E5a.** Прототип упаковщика биграмм в `scripts/` (Python stdlib, по образцу
  `scripts/dictionary_pack.py`), импортирующий `scripts/dictionary_coverage.py::
  normalize_word`; второй набор правил нормализации не заводится.
- **E5a. Источник пар** — `*-sentences.txt` из тех же трёх архивов Leipzig, чьи SHA-256 уже
  запинены в `docs/DICTIONARY-D1A.md` (`tat_mixed_2015_1M`, `tat_news_2015_1M`,
  `tat_web_2018_1M`, суммарно 582 378 373 Б). Новых источников нет. Пайплайн D0/D1A брал
  только `*-words.txt` — из списков частот отдельных слов биграммы не выводятся вообще,
  поэтому распаковывается другой файл того же архива. Архивы и извлечённые файлы в
  репозиторий не попадают. Что именно лежит в `*-co_n.txt` тех же архивов, офлайн не
  проверено; если человек предпочтёт готовый `co_n`, формат и семантику его весов надо
  проверить отдельно, до генерации.
- **E5a. Правила пар:** только соседние токены внутри границ одного предложения; обе формы
  проходят `normalize_word` (NFC, lowercase, только татарский алфавит, ≤ 64 кодпоинта) и
  обязаны входить в уже поставленный top-100k; пара, где успех равен головному слову,
  отбрасывается. Обучение — только `tat_mixed_2015_1M` и `tat_web_2018_1M`;
  `tat_news_2015_1M` целиком held-out, та же схема разделения, что в D1a.
- **E5a. Матрица конфигураций капа по конструкции** (а не по порогу частоты): H — число
  головных слов по unigram-частоте ∈ {5000, 8000, 10000, 15000, 20000}; K — максимум успехов
  на голову ∈ {3, 4, 5}. Явного байта веса нет: порядок успехов фиксируется при упаковке,
  ранг подразумевается позицией (измеренная экономия 25–30%). Для каждой из 15 конфигураций
  записываются: число пар P, размер словника успехов V, сырые байты, сжатые байты (zlib
  level 9, wbits 15, memLevel 9, один Z_FINISH — тот же режим, что в D1a), conditional и
  unconditional top-3 hit-rate, доля событий с доступным предсказанием, peak RSS упаковщика
  и время упаковки. Подсчёт пар выполняется по шардам голов за несколько проходов по
  предложениям: словарь кортежей на миллионы пар иначе не влезает в память, и peak RSS
  обязан быть в отчёте, иначе прототип невоспроизводим на другой машине.
- **E5a. Свидетельство** — `docs/DICTIONARY-E5A.md`: метод, полная таблица 15 конфигураций,
  выбранная конфигурация и явная оговорка о жанровом сдвиге: корпуса новостей и веба
  2015/2018 годов завышают полезность относительно переписки, для которой клавиатура и
  используется, а held-out взят из того же семейства.
- **E5a. Гейт решения** (все условия одновременно): сжатый asset выбранной конфигурации
  ≤ 250 000 Б на язык; сырой ≤ 1 048 576 Б на язык; прогноз APK с двумя языками ≤ 2 800 000 Б
  по формуле «1 446 111 (измеренная база) + 96 256 (дельты E1+E2+E3+E4) + 620 000 (D2) +
  2 × сжатый asset + 20 000 (код E5)», где предшествующие дельты берутся ФАКТИЧЕСКИЕ, если
  фазы уже выполнены; unconditional top-3 hit-rate не ниже порога, согласованного человеком.
  При худшем допустимом asset 250 000 Б прогноз равен 2 682 367 Б, то есть запас до гейта
  ≈ 118 КБ. **Честная оговорка:** байтовый кап при H ≤ 20 000 и K ≤ 5 (не более ≈ 100 000
  пар, что по измеренной модели даёт ≈ 129 000–150 000 Б сжатых) заведомо проходит для всех
  15 конфигураций, поэтому решение фактически опирается ТОЛЬКО на порог полезности. Считать
  прохождение байтового капа прохождением гейта нельзя. Если ни одна конфигурация не
  проходит по полезности — E5b–E5d не начинаются.
- **E5b. Отдельный файл и отдельная схема,** а не расширение `.tdict` schema 1:
  `TdictPrefixIndex.open` и `TdictValidator` жёстко требуют `schemaId == 1`,
  `formatVersion == 1` и точную арифметику секций, а подмешивание биграмм потребовало бы
  пересборки основного 100k-артефакта и смены его запинённых
  `expectedRawSha256`/`expectedEntryCount` при каждом изменении биграмм. Схема: magic
  `TATBIGR\0`, schemaId 2, formatVersion 1, header 96 байт (magic 8 + четыре u16 +
  двенадцать u32 + SHA-256 по смещению 64), checksum по полному сырому файлу с обнулёнными
  байтами дайджеста. Все целые — unsigned little-endian.
- **E5b. Секции** без выравнивания и разделителей: (1) H+1 u32 смещений головных слов;
  (2) UTF-8 блоб головных слов в code-point lexical ascending для бинарного поиска;
  (3) H+1 u32 границ диапазона успехов; (4) P u32 идентификаторов успехов, внутри головы — в
  порядке ранга упаковки; (5) V+1 u32 смещений словника успехов; (6) дедуплицированный UTF-8
  блоб успехов в code-point lexical ascending. Идентификаторы адресуют только словник ЭТОГО
  файла: связи с индексами основного словаря во время исполнения нет, поэтому версии
  артефактов независимы. Порядок успехов внутри головы задаётся один раз при упаковке
  (количество пар descending, при равенстве — code-point ascending); во время исполнения
  переранжирования нет вообще.
- **E5b. Генератор, строгий валидатор, свободно созданные fixtures и тесты:** байт-в-байт
  воспроизводимость при одинаковых входах и версии генератора; отказ на
  malformed/усечённом/склеенном zlib, чужом magic/schema/version/checksum, неканонической
  арифметике секций, невалидном UTF-8, неотсортированных или дублирующихся словах, id ≥ V,
  пустых диапазонах и хвостовых байтах. Собственный guardrail предельного сжатого размера по
  образцу `MAX_COMPRESSED_BYTES`: сборка падает, а не тихо распухает.
- **E5b. Атрибуция:** производная таблица биграмм — отдельный CC BY 4.0 компонент данных, не
  переводимый под Apache-2.0; запись в `assets/.../NOTICE.txt`, полный transformation record
  в `docs/DICTIONARY-E5B.md`.
- **E5b. Хранение** параметризовано языком с самого начала: собственная поддиректория
  device-protected storage (НЕ `filesDir/dictionaries`, где живёт tt-артефакт), имя финального
  файла с идентификатором subtype, собственный regex retention и собственные лимиты.
  Переиспользуются швы `DeviceProtectedDirectoryProvider`, `DurableFileOps`, `StorageClock`,
  `SpaceProbe`, `PreparationResult`/`StorageFailure` и паттерн temp → fsync → validate →
  atomicRename → syncDirectory. Причина отдельной директории:
  `AtomicDictionaryStore.acquireLatestForActivationLocked` координируется процессно по
  каноническому пути директории и вернёт null, если в той же директории жив чужой lease.
  Каталог исключается из резервного копирования теми же правилами, что вводит E4: это
  производная от поставленного в APK ассета, и 250 КБ на язык в квоте бэкапа пользователя
  бессмысленны.
- **E5c. Вид запроса** вводится обязательным полем в `LookupToken` и в `LookupResult`.
  Обоснование — НЕ «иначе токены станут equals»: `LookupToken` несёт `requestSerial`,
  инкрементируемый на каждый `request`, поэтому токены разных запросов не равны и без нового
  поля. Настоящая причина в том, что владелец состояния обязан знать вид результата, чтобы
  выбрать допустимый путь коммита: результат NEXT_WORD нельзя коммитить путём префиксной
  подсказки и наоборот. NEXT_WORD передаёт пустой префикс и непустое нормализованное
  контекстное слово; существующее поведение PREFIX не меняется — пустой префикс по-прежнему
  отвергается и инвалидирует генерацию.
- **E5c. Один вычислитель, один токен.** Оба индекса принадлежат одному
  composite-вычислителю, подставляемому в `MappedDictionaryEngine.startOwnedLease`; он
  отвечает на оба вида запроса внутри ОДНОГО request и одного токена. Второго `request()`,
  второго токена и второго executor нет: `LatestOnlyPrefixEngine` держит одну ячейку
  `currentToken` и один `pendingRequest`, поэтому параллельный запрос физически подавил бы
  первый результат. Если к моменту E5 личный словарь E4 существует, он отвечает внутри того
  же вычислителя; личных биграмм в E5 нет.
- **E5c. Чтение предсказаний:** один бинарный поиск по блоку головных слов, чтение не более
  K идентификаторов u32 и декодирование не более трёх строк. Аллокации — только
  декодированные строки результата, как в существующем `decodeWord`. Подготовка и mmap
  таблицы выполняются лениво и только при включённом тумблере, никогда на UI/cold-start
  пути; освобождение — в том же `Resources.release`, что и основной словарь. Код движка
  размещается в `dictionary/engine`, поэтому попадает под существующий рекурсивный
  `DictionaryEnginePrivacyTest`; при размещении в новом пакете скан расширяется явно.
- **E5d. Письменная поправка «Контракта текста»,** внесённая и отревьюированная ДО кода
  интеграции, поверх текста, уже содержащего редакции E3 и E4: (1) определение текущего
  префикса дополняется отдельным режимом NEXT_WORD; (2) правило «при пустом префиксе
  результаты очищаются» получает единственное исключение — режим NEXT_WORD при включённом
  тумблере; (3) правило ранжирования дополняется тем, что предсказания идут в порядке,
  зафиксированном при упаковке, и во время исполнения не переранжируются; (4) правило
  повторной проверки перед тапом получает отдельный набор проверок для NEXT_WORD; (5)
  таблица состояний полосы дополняется строками для предсказаний, без изменения высоты и
  числа ячеек.
- **E5d. Настройка** `PREF_NEXT_WORD_PREDICTION`, default OFF, добавляется в четыре места по
  образцу `PREF_TATAR_SUGGESTIONS`: ключ в `Settings.java`, статический reader, поле в
  `SettingsValues`, строка `switchRow` в `SettingsHostActivity.buildPreferencesScreen`.
  Тумблер действует только при включённых подсказках; строки en base/ru/tt.
- **E5d. Контекст.** Новые чистые хелперы в `TatarWordUtils`: извлечение контекстного слова
  перед хвостовым пробельным разделителем. Разделитель — один или более U+0020 и ничего
  иного (перевод строки, tab, NBSP и любая пунктуация дают пустой контекст); контекстное
  слово — `extractTrailingWord` от текста перед разделителем; если разделитель или слово
  упираются в нулевой индекс кэша `RichInputConnection` (1024 символа), возвращается пустой
  контекст, потому что истинное начало слова неизвестно.
- **E5d. Сосуществование:** непустой префикс — только префиксные подсказки (весь контракт D1
  без изменений); пустой префикс плюс доступный контекст — только предсказания; смешивания
  источников в одной полосе нет никогда.
- **E5d. Регистр предсказаний:** контекстное слово нормализуется для поиска (NFC +
  lowercase), но его регистр НЕ переносится на предсказание — предсказания показываются и
  вставляются ровно так, как хранит словарь. Смешанный регистр контекста предсказания не
  подавляет (в отличие от правила для префикса), потому что ничего не переносится. Отличие
  фиксируется в поправке контракта.
- **E5d. Отдельный путь коммита** `InputLogic.commitPredictedWord(expectedContextWord,
  suggestion)`: требует collapsed selection, отсутствия буквы сразу после курсора, пустого
  хвостового слова и точного совпадения контекстного слова с живым кэшем; удаляет РОВНО НОЛЬ
  символов; вставляет слово вместе с автопробелом одним `commitText` в одном batch edit по
  существующему правилу `needsAutoSpace`; сбрасывает `mJustDoubleSpaced`/`mLastSpaceDownTime`;
  после успеха пересчитывает shift-состояние тем же вызовом, что и существующий путь.
  Существующий `commitChosenSuggestion` не трогается.
- **E5d. Привязка к subtype** обязательна: новый код не содержит литерала `tt_RU`, язык
  артефакта берётся из активного subtype (шов принадлежит D2), смена языка выполняется
  только полным release + start движка на границе lifecycle по общему правилу раздела
  «Сквозное решение».
- **E5d. Геометрия и a11y не меняются:** та же лениво создаваемая Canvas-полоса 40dp, три
  равные ячейки, три стабильных virtual node ID, пустые ячейки inert и скрыты. Объявление
  TalkBack — только на переходе «пустая полоса → есть слова».

## Открытые вопросы, требующие решения человека

Ни один из этих вопросов агент за человека не решает. Пункты, помеченные **[блокирует]**,
запрещают вход в названную фазу или подфазу до письменного ответа, записанного в
`docs/MILESTONE-v2.md`.

### Сквозные

1. **[блокирует E2b-1 и E5d] Потолок PSS.** Бюджет 30 МБ уже провален на эмуляторе:
   33,4–33,6 МБ с включённой D1 против 29,2–29,4 МБ с выключенной. Сумма заявленных дельт
   будущих фаз даёт ориентировочно 42,7 МБ. Требуется одно из двух: перезамер D1f на
   реальном Samsung становится блокирующим входом в E2, либо потолок пересматривается с
   обоснованием и новым числом, против которого меряются все последующие фазы.
2. **[блокирует E5] Что делать, если биграммы для двух языков не помещаются.** Варианты:
   (а) только татарский, русский без предсказаний — фича асимметрична, бюджет сохранён;
   (б) урезать основные словари ради места — бьёт по главной ценности продукта (held-out D1a
   показывает, что именно 100k держит покрытие 97,87%); (в) осознанно поднять потолок APK
   выше 3 МБ — меняет жёсткий бюджет проекта и требует отдельного письменного решения.
   Инженерного основания предпочесть один вариант другому нет.
3. **[блокирует E4b, E5d] Правки «Контракта текста».** Единая редакция пункта ранжирования
   (три класса кандидатов) и раздел «Контракт личного словаря» принимаются человеком до кода
   E4b; поправка режима NEXT_WORD — до кода E5d.
4. **Вычитка татарских строк носителем языка.** Открыта с D1 и наследуется каждой фазой,
   добавляющей строки (E1b, E2c, E4b, E5d). Машинная или AI-проверка её не закрывает.
5. **Доступ к реальному устройству Samsung/One UI.** Эмулятор не закрывает ни один пункт
   про insets, TalkBack, jank, PSS и latency; часть приёмки E1–E5 без устройства недостижима
   в принципе.

### E1

6. **[блокирует E1a] Порог «тумблер → полоса» и «первое татарское поле → полоса».**
   Предложение — p95 1 000 мс; число утверждает владелец. От него зависит, становится ли
   кэширование результата валидации обязательной подфазой E1d.
7. Момент показа предложения: сразу при первом показе клавиатуры с активной татарской
   раскладкой (проще, ловит пользователя с единственным татарским subtype) или после первого
   набранного татарского слова (приходит к тому, кто уже печатает по-татарски, но требует
   дополнительного состояния).
8. Форма предложения: модальный диалог поверх окна IME (инженерный выбор — переиспользует
   проверенный путь, ноль риска для insets, touchable region и a11y) или одноразовая
   полоска-баннер над клавиатурой (визуально мягче, но требует нового `ViewStub`, правки
   `getVisibleInputBounds` и `onComputeInsets` и удваивает объём фазы). Баннер — отдельная
   подфаза, а не правка E1b.
9. Тексты предложения на трёх языках и подписи кнопок.
10. Нужен ли в настройках явный пункт «Удалить распакованный словарь». Решение E1a-8
    оставляет 2 542 036 Б на диске после выключения; явный пункт вернул бы контроль, но
    требует нового destructive-пути в хранилище и отдельной подфазы.
11. Освобождать ли словарь по существующему таймеру `MSG_DEALLOCATE_MEMORY` (10 с после
    скрытия клавиатуры). Выигрыш по проваленному PSS заметен, плата — повторные
    `acquireLatestForActivation` (полная валидация) и mmap при каждом показе клавиатуры.
    Нужен замер прежде решения.
12. Освобождать ли словарь при уходе с татарского subtype при включённой настройке. Сейчас
    engine остаётся живым; для двуязычного пользователя это постоянные ≈ 4,2 МБ PSS, но
    частые переключения глобусом сделали бы освобождение дорогим. Влияет и на D2.
13. Что делать при `Unavailable` после того, как пользователь явно включил тумблер. Выбор по
    умолчанию — молчать (fail-closed), но тогда человек включил переключатель и не получил
    ничего без объяснения. Альтернатива — разовое сообщение; это продуктовое решение.

### E2

14. Какую версию Unicode пинить для `emoji-test.txt`. Более новая даёт больше записей,
    которых заведомо нет в шрифтах Android 7–9 и которые всё равно отфильтрует проба.

### E3

25. Заполнять ли ячейки неточными кандидатами, когда точных нашлось 1–2, или только когда
    точных нет вовсе. Первое срабатывает на 12,5% корректно набранных префиксов (на длинных
    — до 43%), второе — на 4,3%. По умолчанию заложен первый вариант.
26. Отличать ли неточные кандидаты визуально и объявлять ли их иначе в TalkBack. Любой такой
    знак — правка замороженного контракта полосы, поэтому в E3 не заложен.
27. Выпускать ли класс «пропущенная буква» (E3c) с учётом +4,2 п.п. за восьмикратный рост
    числа вариантов. Решение принимается после замеров E3b на реальном устройстве.
28. Нужен ли отдельный пользовательский тумблер для нечётких подсказок. Рекомендация — нет:
    нечёткий уровень не может ухудшить уже работавшую подсказку, а каждый тумблер стоит поля
    в `SettingsValues`, трёх переводов и нового сочетания состояний в матрице тестов.
29. Минимальная длина префикса 3 кодпоинта — подтвердить. Вариант «разрешить диакритические
    пары с двух букв» дёшев (не более двух вариантов), но повышает шум.
30. Обязательна ли вычитка носителем языка новых кандидатов из

    соседи» (fanout падает с 3,51 до 2, шум меньше, recovery ниже) или подобрать по живому
    тесту на устройстве.
