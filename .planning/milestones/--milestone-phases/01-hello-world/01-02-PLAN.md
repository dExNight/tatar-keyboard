# Plan 01-02 — Подпись release и CI-гарантия PERF-04 (wave 2)

**Goal:** `assembleRelease` даёт подписанный APK (задел REL-01); репозиторий живёт на GitHub, и CI на каждом коммите доказуемо падает при появлении разрешения INTERNET (PERF-04) — негативный тест продемонстрирован.

Vertical-slice дисциплина: после Task 1 пользователь может поставить release-сборку; после Task 2 каждый пуш автоматически собирает и проверяет APK; Task 3 доказывает, что гарантия — не декорация.

## Context

- Зависит от plan 01-01: форк смержен, `scripts/check-no-internet.sh` существует, applicationId `org.tatarkeyboard.ime` зафиксирован.
- Источник паттернов: `.planning/phases/01-hello-world/01-RESEARCH.md` — Pattern 3 (условный signingConfig), Pattern 4 (CI workflow), Pitfalls 6–7.
- GitHub-репозиторий создаётся здесь (публичный: проект open-source Apache-2.0 по PROJECT.md/CONTEXT; CI = GitHub Actions — решение CONTEXT.md). До первого пуша обязательна проверка истории на секреты (T1).

Затем сгенерировать в корне репозитория `release.jks` командой keytool из Pattern 3: alias `tatarkeyboard`, `-keyalg RSA -keysize 4096 -validity 10950`, non-interactive (`-storepass`/`-keypass` — сгенерированный пароль, например `openssl rand -base64 24`, плюс `-dname` вида CN=Tatar Keyboard). ## Flagged assumptions (edge-coverage fallback, no silent drops)

- **PERF-04 edge-probe row: `unclassified` → `unresolved` — surfaced, не auto-backstopped.** Edge-probe отчёт классифицировать PERF-04 не смог (probe: «unclassified — review manually»). Ручной разбор планировщика: PERF-04 — бинарное конфигурационное must-NOT-требование, а не data-shape edge, поэтому таксономия его не берёт. Разрешение в этом плане: явная truth №1 (двухуровневая проверка + CI) и негативный тест Task 3 как механическое доказательство. Верификатор обязан подтвердить именно свидетельство негативного прогона (failure на ci-negative-test); без этого свидетельства критерий не считается закрытым.
- **GitHub-репозиторий публичный** — следует из open-source Apache-2.0 (PROJECT.md) и решения CONTEXT «git/GitHub → GitHub Actions»; если пользователь предпочтёт приватный на время разработки, CI-логика не меняется (Actions работают и в private) — сменить видимость можно без правок плана.
- **Первый CI-прогон может упасть на лицензиях SDK** (Pitfall 7) — тогда добавить в workflow шаг `yes | sdkmanager --licenses` до Gradle; это предусмотренный fallback, не отклонение от плана.
