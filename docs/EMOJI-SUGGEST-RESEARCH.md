# EMOJI-SUGGEST-RESEARCH — ресерч эмодзи-подсказок в полосе (2026-09-01)

Только исследование; код не менялся. Вопрос: стоит ли предлагать эмодзи в полосе
подсказок, когда пользователь набрал слово («самолет» → ✈️), и во что это обойдётся
для ru/tt. Ответы — ниже; план реализации — `docs/EMOJI-SUGGEST-PLAN.md`.

## 1. Как это делают другие

| Клавиатура | Триггер | Семантика тапа | Тоггл |
|---|---|---|---|
| **Gboard** | завершённое слово | **append** (эмодзи добавляется, слово не трогается) | отдельный, per-language |
| **iOS (QuickType)** | завершённое слово | **replace** (слово заменяется эмодзи) — при ошибке разрушительно | нет отдельного (источник жалоб) |
| **SwiftKey** | даже незавершённое слово (антипример) | append/replace | отдельный + персональное обучение |
| **Samsung** | завершённое слово | append | два тоггла (эмодзи/стикеры) |

Open-source клавиатуры (FlorisBoard, OpenBoard, наследники AOSP) фичи не имеют —
готового кода рядом нет.

## 2. UX-правила (из чужих ошибок, зафиксированы жалобами пользователей)

1. Только **завершённое слово**, не префикс (SwiftKey «lau»→😂 — антипример).
2. **Append, не replace** (модель Gboard; модель iOS разрушает слово при ошибке).
3. Отдельный слот полосы, словарные подсказки **не вытесняются**.
4. Отдельный тоггл в настройках (iOS без него — антипример).
5. Никаких попапов/вибрации/звуков при появлении эмодзи (Gboard 2022 — взрыв жалоб).
6. Те же гейты приватных полей, что у подсказок слов.

## 3. Данные: замеры на наших ассетах

- `emoji_search_v1.txt` (CLDR 44 + ru/en + наши 200 tt-синонимов из миссии m2):
  точный матч top-1000 русских слов → 194 хита, из них ≥4 букв — 157.
- **CLDR напрямую нельзя**: false positives неприемлемы — «можно»→🚬,
  «работа»→😫, «нет»→😑, «день»→🥳. Хорошие хиты есть: «сердце»→💘,
  «самолет»→✈️, «кошка»→🐱.
- **Словоформы — главная проблема**: CLDR хранит леммы; «сердца» есть,
  «сердцу» — нет. Лемматизатор невозможен (ноль зависимостей, бюджет).
  Наивный стемминг замерен и отвергнут (мусор: «ведь»→«ведьма»).
- CLDR для tt пуст полностью (4 записи, все про пунктуацию) — татарский маппинг
  только ручной. Наши 200 tt-синонимов — фундамент.

**Вывод по данным**: единственный работающий путь — курируемый ассет
«слово/словоформы → эмодзи» (~300–800 понятий), генерируемый нашим
python-конвейером с пинами SHA-256, гардианами и golden-тестами, в духе проекта.

## 4. Стыковка с нашим кодом (проверено по коду)

Переиспользуется почти всё:

- **Паттерн companion-fill** (`SuggestionsController.applyCompanionResult`,
  `SuggestionsController.kt:1283–1325`) — источник, дополняющий ячейки полосы
  с конца, не вытесняя занятые. Готовый seam для эмодзи-источника.
- **`InputLogic.commitPredictedWord`** (`InputLogic.java:672–722`) — «вставить,
  ничего не удаляя, + автопробел», со всеми stale-защитами. Ровно семантика
  эмодзи-кандидата. Вариант A не требует новых путей вставки вообще.
- **Гейты приватности** наследуются: opt-in, `mShouldShowSuggestions` (пароли),
  `IME_FLAG_NO_PERSONALIZED_LEARNING` (`LatinIME.java:1132–1142`).
- **Производительность**: ассет ~10–30 КБ, парсинг единицы мс, запрос —
  HashMap-lookup. Не проблема.
- **A11y**: contentDescription ячейки должна озвучивать имя эмодзи (готовое
  `resultNameAt` из EmojiSearchIndex).

## 5. Варианты и оценка

| Вариант | Суть | Трудоёмкость | Риск |
|---|---|---|---|
| **A (рекомендован)** | Слово + пробел → эмодзи в NEXT_WORD-полосе рядом с биграммами | ~4–5 дней, половина — курирование таблицы | низкий; текстовый контракт не трогается |
| B (как Gboard) | Эмодзи, пока слово ещё под курсором | ~6–7 дней | средний: новый путь вставки в «замороженный» InputLogic |

## 6. Вердикт

Реализовывать стоит: органичное расширение существующего эмодзи-поиска; ни в одной
клавиатуре нет татарского emoji-suggest (конкурентное преимущество — ЦА
билингвальна). Только: вариант A, курируемые данные, append, отдельный тоггл.
Главная цена — не код, а курирование таблицы слово→эмодзи со словоформами
(русская флексия + татарская агглютинация).
