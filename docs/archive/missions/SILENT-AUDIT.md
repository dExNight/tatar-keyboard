# Аудит молчаливых отказов и неоткатываемого состояния в подсказках

Миссия `tt-silent-audit`. Роль читающая: **кода эта миссия не меняла ни строки**, наружу
ничего не отправлялось. Ветка `version-1.6.0`, дерево на коммите `812e4bf`.

## Область и метод

Разобрана подсистема подсказок целиком: `latin/suggestions/`, `latin/dictionary/`
(`engine`, `personal`, `personalstore`, `storage`), три пути вставки текста в
`inputlogic/InputLogic.java`, их обвязка в `LatinIME.java` и кэш `RichInputConnection.java`
— около 13 200 строк. Чтение сплошное по путям, а не по грепу; каждая находка ниже
прослежена от пользовательского действия до строки, которая его гасит.

**Класс A — молчаливый отказ.** Пользователь совершил действие, система его не выполнила и
ничем об этом не сообщила: ни текстом, ни состоянием полосы, ни логом. Сюда же — рапорт об
успехе, выданный до того, как результат стал известен.

**Класс B — неоткатываемое состояние.** Состояние изменено так, что вернуть прежнее
пользователь не может: либо потому что данные уничтожены без копии, либо потому что
одноразовый флаг израсходован, либо потому что «стирание» на экране разошлось с диском.

Классы пересекаются, и самое дорогое лежит именно в пересечении: подтверждённое
разрушающее действие, которое молча не выполнилось.

### A1. Явное включение подсказок теряет провенанс

`requestPreparationIfNeeded` отсекает повторный запрос **раньше**, чем успевает записать,
кем он был вызван:

```kotlin
if (slot.preparationRequested) return          // :878
…
slot.preparationRequested = true
slot.preparationRequestedByExplicitEnable = explicitEnable   // :884
```

`preparationRequestedByExplicitEnable` — «первый писатель выигрывает». Сценарий:

1. Настройка уже включена, пользователь открывает поле → `onStartInput` →
   `requestPreparationIfNeeded()` **без** `explicitEnable`. Флаг встал, распаковка словаря
   пошла в фон (реальные сотни миллисекунд: разжатие и валидация артефакта).
2. Полоса не появляется, пользователь идёт в настройки и щёлкает тумблер OFF → ON.
3. `onSuggestionsSettingEnabled` сбрасывает `preparationRequested` только при
   `lastPreparationUnavailable` — а подготовка ещё **в полёте**, результата нет. Флаг
   остаётся, `requestPreparationIfNeeded(explicitEnable = true)` выходит на `:878`.
4. Подготовка заканчивается `Unavailable`. Провенанс — «не явный», значит
   `dictionaryUnavailableListener` не дёргается вообще.

`SuggestionsOfferController` со всей своей машинерией отложенного показа (семь условий
окружения, повтор на границе `onInputViewStarted`, отмена при обратном выключении) в этом
сценарии **не вызывается ни разу**: до него не доходит событие. Пользователь щёлкнул
тумблер и не получил ни полосы, ни сообщения — ровно то, что комментарий на
`DictionaryUnavailableListener` называет недопустимым: «leaving that unanswered would look
like the setting simply did nothing».

Восстановимо: после `Unavailable` флаг `lastPreparationUnavailable` встаёт, и **следующий**
цикл OFF → ON уже пройдёт как явный. То есть цена — один потерянный щелчок, а не
постоянная немота.

Тестов на провенанс нет: `dictionaryUnavailableListener` не упоминается ни в одном тесте,
`SuggestionsOfferControllerTest` покрывает только то, что происходит **после** вызова
слушателя.

### A2. Экран личного словаря рапортует успех до записи

Все три обработчика устроены одинаково: поставить мутацию в очередь и тут же перерисовать
экран.

```kotlin
val added = subtypeId != null && controller.addWord(subtypeId, field.text.toString())
if (!added) { Toast … personal_dictionary_add_rejected }
showScreen(Screen.PERSONAL_DICTIONARY)          // :477
```

`addWord` возвращает `true`, как только слово **прошло фильтр содержимого**, — то есть
отвечает на вопрос «слово допустимо», а не «слово сохранено»:

```kotlin
PersonalDictionaries.storeFor(context, subtypeId).addManually(trimmed)
return true
```

`addManually` — это `onWorker { … }`, событие на единственном фоновом воркере, где
`commitWrite` обновляет `snapshot` **только при успешной** `writeWhole` (temp → fsync →
ревалидация → atomic replace → fsync каталога). `showScreen` при этом синхронно читает
`snapshotFor(...)`, то есть тот же `@Volatile snapshot`.

Отсюда два разных дефекта в одном месте:

* **Гонка перерисовки** (высокая вероятность, низкая цена): экран почти всегда
  перечитывает снимок раньше, чем воркер успел сделать две fsync. Добавленное слово не
  появляется в списке, удалённое — остаётся. Пользователь видит «кнопка не сработала» и
  жмёт ещё раз.
* **Настоящий провал записи** (низкая вероятность, высокая цена): нет места
  (`spaceProbe.usableBytes < bytes + 64 KiB` → `writeWhole` возвращает `false`),
  ревалидация не прошла, каталог не создался. Тогда слово не появится **никогда**, и ни
  тоста, ни лога, ни повторной попытки не будет. Тост `add_rejected` покрывает только
  отказ фильтра и на этот путь не приходит.

То же дословно относится к `removeWord` (`:489`) и `eraseAll` (`:503`) — с той разницей,
что там молча не выполняется **подтверждённое разрушающее действие**.

### A3. Провал «Забыть слово» полностью нем

`PersonalDictionaryStore.forget` (`:125`):

```kotlin
val candidate = entries.remove(normalized)
if (candidate === entries) return@onWorker
if (candidate.isEmpty) {
    if (deleteFile()) { entries = candidate; snapshot = PersonalDictionary.EMPTY }
} else {
    commitWrite(candidate)                      // :146 — при провале не делает НИЧЕГО
}
```

`commitWrite` при неудачной `writeWhole` не трогает ни `entries`, ни `snapshot`. Слово
остаётся и в памяти, и на диске.

Но пользователю уже сказали обратное. `PersonalForget.confirmForget` сразу после постановки
в очередь зовёт `notifyErased()`, что доходит до `SuggestionsController.onPersonalDictionaryErased()`
и **очищает полосу**. Диалог закрылся, слово из полосы исчезло — визуально удаление
состоялось. На следующем наборе того же префикса слово возвращается.

Асимметрия внутри самого метода: pending-хеш слова снимается **до** попытки записи и
безусловно (`:131-136`), а сама запись может не состояться. То есть при провале прогресс
обучения потерян, а слово — нет.

### A4. Пути вставки текста рапортуют успех при отсутствующем InputConnection

`RichInputConnection.commitText` правит локальный кэш **безусловно**, а IPC делает только
при живом соединении:

```java
mTextBeforeCursor += text;                      // :247 — всегда
if (hasCursorPosition()) { mExpectedSelStart += text.length(); … }
if (isConnected()) { mIC.commitText(text, newCursorPosition); }   // :255 — только если есть
```

`deleteTextBeforeCursor` устроен так же (`:374-385`). `beginBatchEdit` обновляет `mIC`
свежим `getCurrentInputConnection()`, который у отсоединившегося редактора возвращает
`null`.

`replaceTrailingWord` (`InputLogic.java:552`) после батча возвращает `true`
**безусловно** — проверки `isConnected()` в нём нет. Через него идут оба первых пути
вставки; третий, `commitPredictedWord`, устроен идентично.

Следствие двойное:

* **Класс A.** `SuggestionsController.onTap` получает `true`, считает слово вставленным,
  снимает привязку и очищает полосу. В редакторе не появилось ничего.
* **Класс B.** Кэш теперь содержит текст, которого в редакторе нет, а `mExpectedSelStart`
  уехал. Все последующие решения — извлечение префикса, `hasLetterAfterCursor`, проверка
  «слово ещё то же самое» перед автокоррекцией, суффиксная проверка отмены — принимаются
  по фикции. Автокоррекция в этом состоянии внутренне непротиворечива (её отмена сверяется
  с тем же кэшем и «проходит»), но обе правки — призрачные.

Разъезд лечится только `clearCaches()` / перечиткой на следующей границе ввода. Признаю
низкую вероятность: путь требует, чтобы соединение отвалилось между показом подсказки и
тапом. Наследственная черта базы Simple Keyboard, но `true` без проверки — это уже новый
код подсказок.

### A5. «Стёрто значит стёрто» — гонка, а не гарантия

`PersonalForget.confirmForget` (`:47`):

```kotlin
PersonalDictionaries.storeFor(context, subtypeId).forget(normalized)   // в очередь
PersonalDictionaries.notifyErased()                                    // немедленно
```

`forget` — событие на воркере, завершающееся полной перезаписью файла с двумя fsync.
`notifyErased` выполняется сразу. Между очисткой полосы и обновлением `snapshot` есть
окно, в котором движок читает **старый** снимок. Нажатие клавиши в этом окне может снова
показать «стёртое» слово, и тап по нему пройдёт обычным путём коммита.

Комментарий на `onPersonalDictionaryErased` формулирует требование точно — «для функции,
вся ценность которой в „стёрто значит стёрто“, это дефект самой гарантии» — и закрывает
ровно половину задачи: полоса отвязывается немедленно, но источник, который она читает,
отстаёт на одну запись с fsync. На бюджетном устройстве (целевом для проекта) это
десятки–сотни миллисекунд.

### B1. «Стереть всё»: первое исключение оставляет соль и счётчики

`clearAll` (`:155`) чистит память первой, файлы — потом, тремя вызовами в одном `try`:

```kotlin
entries = …empty; pending = EMPTY; salt = null; snapshot = EMPTY; loaded = true
if (!unlockGate()) return@onWorker                 // :163 — память пуста, файлы целы
try {
    deleteFile()                                   // .tpers
    deleteFile(directory, File(directory, pendingFileName()))
    deleteFile(directory, File(directory, SALT_FILE_NAME))
} catch (_: Exception) { }                         // :169
```

`deleteFile(directory, file)` бросает `IOException`, если файл существует и не удалился.
Исключение на **первом** вызове пропускает два остальных. Результат: экран показывает
пустой список (память уже чиста), а на диске остаются и словарь, и `pending-*.bin`, и
`salt.bin`. При следующем старте процесса `open()` перечитывает файл и `readPending`
возвращает счётчики — слова возвращаются, включая те, что стояли на 2/3 пути к
запоминанию, и дозапоминаются после трёх новых наборов. Соль та же, так что хеши сходятся.

Ветка `:163` даёт то же самое без всякого исключения: память вытерта, диск не тронут. С
экрана настроек она недостижима (устройство там разблокировано по определению), но
`clearAll` — публичная точка стора.

Ни один из путей ничего не сообщает: `catch` пуст по privacy-политике проекта (не логировать
путей и текста), а вызывающая сторона результата не ждёт — см. A2.

### B2. Повреждённый `.tpers` уничтожается без копии и без уведомления

`open()` (`:256`):

```kotlin
if (validated == null) {
    runCatching { deleteFile(directory, file) }   // карантин без копии
    entries = PersonalEntries.empty(maxEntries)
    snapshot = PersonalDictionary.EMPTY
    return true
}
```

Любая неудача валидации — обрезанный файл после отключения питания, несовпадение
контрольной суммы, будущее изменение формата — стирает **весь** личный словарь
пользователя безвозвратно. Копии не остаётся, сообщения нет, и `loaded = true` уже
выставлен, так что до конца процесса стор молча пуст.

Решение задокументировано в самом коде («quarantine — no copy is kept») и согласуется с
fail-closed-политикой. Регистрирую не как ошибку реализации, а как **принятое решение с
неоткатываемым последствием**, которое стоит назвать вслух: единственные данные, которые
эта клавиатура хранит о пользователе, уничтожаются без подтверждения и без следа.

### B3. `forget` — единственная мутация без `try/catch`

Обратная крайность того же места. Все прочие мутации стора ловят исключения:
`addManually` → `commitWrite` → `writeWhole` (полностью в `try`), `flush` → `writeWhole` /
`writePending` (оба возвращают `false`), `prime` → `open` (в `try`), `clearAll` (в `try`).

`forget` (`:125`) — нет. Внутри него `deleteFile()` (`:377`) устроен так, что **никогда не
возвращает `false`**: он либо возвращает `true`, либо пробрасывает `IOException` из
двухаргументного варианта (`:383`). Проверка `if (deleteFile())` на `:141` поэтому
бессмысленна, а исключение уходит из лямбды наружу.

Лямбда попадает на воркер через `executor.execute(block)`. Воркер создан как
`Executors.newSingleThreadExecutor { Thread(runnable, "personal-dictionary").apply { isDaemon = true } }`
— без `UncaughtExceptionHandler`. Непойманное исключение в фоновом потоке приложения
доходит до `KillApplicationHandler` и убивает процесс IME.

То есть удаление **последнего** слова личного словаря при неудаче `File.delete` роняет
клавиатуру, а не отказывает молча. Вероятность мала (собственный device-protected каталог
приложения), но `clearAll` оборачивает те же вызовы в `try` — значит, авторы считают их
способными бросить.

## Что проверено и оказалось закрытым

Честности ради — эти гипотезы не подтвердились, и это тоже результат:

* **Присоединение bigram-таблицы к уничтоженному движку.** `maybeAttachBigramSource`
  отдаёт колбэк на фоновый воркер без повторной проверки `destroyed`, но
  `MappedDictionaryEngine.attachBigramSource` внутри `synchronized(lock)` проверяет
  `released` и бросает `AttachRacedDestroy` с корректным освобождением лиза
  (`MappedDictionaryEngine.kt:88-107`). Гонка закрыта уровнем ниже.
* **Потеря tap-слушателя при ленивом создании полосы.** Закрыто ранее (аудит D1):
  `setTapListener` перевешивается в `onStartInput`, `onSubtypeChanged` и
  `onSuggestionsSettingEnabled`.
* **Тап по устаревшему кандидату.** Двойная защита держится: `displayedPrefix` /
  `displayedContextWord` привязаны к сессии и снимаются во всех шести местах, а
  `replaceTrailingWord` независимо перепроверяет живой кэш.
* **Отмена автокоррекции после внешнего перемещения курсора.** `onUpdateSelection`
  корректно отделяет собственные правки через `externalMove`, жесты курсора идут через
  `onSuggestionsAffectingCursorMove`.
* **Сброс окна отмены до попытки** (`maybeRevertAutocorrect` роняет `revertable` первым) —
  задокументированное намерение «ровно одна отмена», не дефект.
* **`spendOffer()` до показа диалога** — задокументированное направление отказа («показать
  ноль раз допустимо, два раза — нет»). Неоткатываемо по замыслу.
* **Граница кэша в 1024 символа.** `extractNextWordContext` защищает её явно и возвращает
  `""`; `extractTrailingWord` — нет. Асимметрия реальна, но практически недостижима:
  непрерывный ряд из 1024 буквенных символов не даст ни кандидатов в словаре, ни совпадения
  `advice.typedWord`, так что до путей вставки дело не доходит. Регистрирую как замечание,
  не как дефект.
* **51 «немой» `catch` в подсистеме** — просмотрены все. За вычетом B3 это осознанные
  fail-closed-ветки очистки лизов и отображений; privacy-политика проекта (не логировать
  путей и набранного текста) делает их немыми по построению.

## Сквозное наблюдение

Оба класса растут из одного корня: **подсистема последовательно выбрала fail-closed и
запрет на логирование, но не завела ни одного канала обратной связи о неудаче.**
Единственный такой канал — `DictionaryUnavailableListener` с его одним диалогом, и именно
его A1 обходит. Всё остальное — записи в личный словарь, удаления, стирание, вставки
текста — не имеет способа сообщить о провале даже разработчику, потому что лог запрещён, а
результат никто не ждёт.

Отсюда практический вывод для приоритизации: **A2 стоит первым не по вероятности провала
записи, а потому что это единственное место, где пользователь регулярно видит расхождение
своими глазами** (нажал «Добавить» — слова нет в списке). A3, A4, B1 редки, но
разрушительны и невидимы. B2 и B3 — принятые решения, которые стоит перечитать глазами
оператора, а не чинить по умолчанию.

## Границы аудита

* Читающая миссия: код не менялся, тесты не запускались, на устройстве ничего не
  проверялось. Все выводы — из чтения исходников на `812e4bf`.
* Вероятности в таблице — инженерная оценка по достижимости пути, а не измерение.
* За рамками осталось: панель эмодзи, раскладки, тема оформления, сборка и артефакт.
* Экран настроек разобран только в части личного словаря.
