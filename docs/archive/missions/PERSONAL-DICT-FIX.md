## Сквозное решение, из которого выросли все шесть правок

Аудит закончился наблюдением, что подсистема выбрала fail-closed и запретила себе логи,
**но не завела ни одного канала обратной связи о неудаче**. Поэтому починка ни одной из
находок не сводилась к «вернуть false наверх»: возвращать было некуда.

Канал построен и выглядит так:

```
store (воркер)  ──PersonalMutationOutcome(Boolean)──▶  экран / IME  ──▶  человек
```

`PersonalMutationOutcome` (`PersonalStorageSeams.kt:59`) — один булев и больше ничего.
Ни слова, ни пути, ни причины: privacy-политика пакета запрещает им покидать стор, и
именно поэтому наверх едет булев, а не сообщение. `PersonalStorePrivacyTest` продолжает
проходить без изменений.

Все три мутации стора (`addManually`, `forget`, `clearAll`) получили необязательный
параметр `outcome`, вызываемый **на воркере после того, как запись состоялась или не
состоялась**. Значение по умолчанию `null` — все существующие вызовы и тесты не тронуты.

Дальше `PersonalDictionaryScreenController` перекладывает ответ на UI-поток через
`uiPoster`, а `SettingsHostActivity.afterPersonalMutation()` (`:526`) — единственное
место, где экран решает, что человек увидит: тост при неудаче и перерисовка списка,
теперь по завершении, а не в том же операторе.

## По находкам

### A1 — провенанс явного включения. Починена

`requestPreparationIfNeeded` отсекал повторный запрос **раньше**, чем успевал записать,
кем он вызван, и явное включение, пришедшее пока распаковка ещё в полёте, терялось.
Правка (`SuggestionsController.kt:887`) — три строки: дедупликация запроса остаётся, но
провенанс апгрейдится.

```kotlin
if (slot.preparationRequested) {
    if (explicitEnable) slot.preparationRequestedByExplicitEnable = true
    return
}
```

Апгрейд односторонний: открытие поля не понижает уже висящий явный запрос до анонимного,
иначе сообщение терялось бы при обратном порядке тех же двух событий.

**Тест:** `DictionaryUnavailableProvenanceTest`, три случая — явное поверх неявного
(сообщение есть), неявное поверх явного (сообщение есть), чисто неявное (тишина, как и
задумано).

**Проверка, что тест ловит дефект:** с откаченной строкой апгрейда
`turningTheSettingOnWhileAPreparationIsInFlightStillAnswersTheUser` падает; с правкой —
зелёный. Прогонял оба состояния.

### A2 — экран рапортовал успех до записи. Починена

Два дефекта в одном месте, оба закрыты.

**Гонка перерисовки.** `showScreen(...)` стоял в том же операторе, что и постановка
мутации в очередь, и читал снимок, которого ещё не существовало. Теперь перерисовка
живёт в `afterPersonalMutation` и вызывается по факту. Единственная синхронная
перерисовка, которая осталась в обработчике «Добавить», — на ветке отказа фильтра
содержимого, где в очередь ничего не попадало и ждать нечего.

**Настоящий провал записи.** `addWord` по-прежнему возвращает «слово допустимо»
синхронно — это честный и немедленный ответ про само слово. «Слово сохранено» — другой и
более поздний ответ, и он приходит колбэком.

`eraseAll` сложнее остальных: языков несколько, а сообщение должно быть одно.
Контроллер считает ответы и отдаёт `true` только когда **у всех** языков файлы ушли;
любая частичная неудача топит общий ответ. Частичное стирание, отрапортованное как
успех, — худший из трёх исходов: экран показывает пустой список, а слова возвращаются
при следующем старте процесса.

**Тесты:** сторона стора — `PersonalDictionarySilentFailureTest`, настоящие JVM-тесты на
реальном каталоге. Сторона экрана — `PersonalDictionaryFeedbackSourceContractTest`,
source-contract, потому что `Activity` off-device не запускается; это уже принятый в
проекте способ для этого класса (`PersonalDictionaryScreenSourceContractTest`,
`PersonalDictionarySettingsTest` написаны так же).

**Проверка, что тесты ловят дефект:** контрактный файл прогонялся против настоящих
до-правочных исходников (`git show HEAD:…` для `SettingsHostActivity.kt`,
`PersonalDictionaryScreenController.kt`, `LatinIME.java`, `PersonalForget.kt`) —
**6 из 8 тестов красные**. Два оставшихся зелёными — проверка строк (строки я не
откатывал) и самопроверка на fail-capability.

### A3 — провал «Забыть слово» был полностью нем. Починена

Слово удаляется из двух мест, и оба теперь отвечают.

* **Экран настроек** → тост «Не удалось удалить слово. Оно осталось в словаре.»
* **Долгое нажатие на полосе в самой клавиатуре** → `PersonalForget.confirmForget`
  получил необязательный `onFailed: Runnable?`; `LatinIME` показывает диалог
  (`showPersonalForgetFailedDialog`, `:854`) — той же формы и с тем же креплением к окну
  ввода, что уже существующий `showSuggestionsUnavailableDialog`. Диалог, а не тост, по
  той же причине, что записана там: тост из фонового процесса показывается на усмотрение
  платформы, а другого канала у этого пути нет.

Отвязка полосы осталась немедленной — это и есть гарантия «стёрто значит стёрто», её
ждать нельзя. Отвечает только сама запись.

**Оговорка, которую надо назвать вслух:** у ветки «удаляем последнее слово» отказ
по-прежнему не тихий, а фатальный — это B3, и он вынесен оператору. Пока B3 не решён,
A3 закрывает провал перезаписи (слов больше одного), но не провал удаления файла.

### A4 — пути вставки рапортовали успех при отсутствующем соединении. Починена

`replaceTrailingWord` (пути 1 и 2) и `commitPredictedWord` (путь 3) спрашивают о
соединении сразу после `beginBatchEdit()` — раньше нельзя, именно он обновляет `mIC` из
фреймворка — и при его отсутствии не трогают ни кэш, ни редактор, возвращая `false`.

Форма выбрана не первая пришедшая. Ранний `return false` с собственным `endBatchEdit()`
ломал замороженный контракт текста, который `AutocorrectSourceContractTest` пинает
дословно: «ровно одно удаление, ровно один коммит, ровно один batch edit». Поэтому
проверка оформлена флагом:

```java
mConnection.beginBatchEdit();
final boolean connected = mConnection.isConnected();
if (connected) { … одно удаление, один коммит … }
mConnection.endBatchEdit();
if (!connected) { return false; }
```

Одно открытие, одно закрытие на любой ветке, чужой тест не тронут.

`SuggestionsController.onTap` уже сегодня обрабатывает `false` правильно: привязка не
снимается, полоса не чистится. Отдельной правки там не понадобилось.

**Тест:** `CommitPathConnectionContractTest` — source-contract, потому что `InputLogic`
требует живой `InputMethodService`, `KeyboardSwitcher` и синглтон
`RichInputMethodManager`. Проверяет наличие проверки, её место (после `beginBatchEdit`,
до любой записи, причём удаление тоже под охраной) и сохранность правила «один batch».

**Проверка, что тест ловит дефект:** обе охраны вырезаны из `InputLogic.java` скриптом —
2 теста из 4 красные; охраны возвращены — зелёные.

### A5 — «стёрто значит стёрто» было гонкой. Починена

Удаление публикуется читателям **до** записи, а не после неё:

```kotlin
val previousSnapshot = snapshot
snapshot = if (candidate.isEmpty) PersonalDictionary.EMPTY else candidate.toSnapshot(subtypeId)
val removed = if (candidate.isEmpty) deleteFile() else writeWhole(candidate)
if (removed) entries = candidate else snapshot = previousSnapshot
```

Окно, в котором движок мог прочитать старый снимок и вернуть стёртое слово на полосу,
схлопывается с «сериализация + две fsync + ревалидация» до «переход события на воркер».

Вторая половина правки не менее важна первой: при неудачной записи снимок
**восстанавливается**. Слово в этот момент действительно осталось сохранённым, и делать
вид, что его нет, — та же ложь в другую сторону, только уже постоянная.

**Тест:** `theErasedWordIsGoneFromThePublishedSnapshotBeforeTheWriteBegins` читает
опубликованный снимок **из середины самой записи** — то есть наблюдает окно изнутри — и
`aFailedErasureRestoresThePublishedSnapshot` на обратный случай.

**Проверка, что тест ловит дефект:** порядок возвращён к до-правочному (запись, потом
публикация) — тест красный; правка на месте — зелёный.

### B1 — «Стереть всё» бросало соль и счётчики. Починена

Три удаления были в одном `try`, и исключение на первом пропускало два остальных. Теперь
каждое живёт само по себе (`deleted { … }`, `:282`), и результат — конъюнкция трёх.

То, что оставалось на диске, — не безобидный мусор: соль та же, значит хеши сходятся, и
слова, стоявшие на 2/3 пути к запоминанию, сохраняли прогресс и дозапоминались после трёх
новых наборов — при пустом списке на экране.

Ветка `if (!unlockGate())` теперь тоже отвечает `false`: память вытерта, диск цел, при
следующем старте процесса всё возвращается — ровно тот случай, который не должен
проходить за успех.

**Тест:** `erasingEverythingStillRemovesTheSaltAndTheCountersWhenTheDictionaryCannotBeDeleted`
роняет удаление только `.tpers` и требует, чтобы соль и счётчики всё равно ушли; плюс
тест на ветку гейта и на обычный путь.

**Проверка, что тест ловит дефект:** общий `try` возвращён — тест красный; правка на
месте — зелёный.

### B2 — повреждённый `.tpers` уничтожается без копии. Вынесена оператору

Не чинил: аудит назвал это принятым решением, а досье запрещает переделывать такие
решения молча.

Что, на мой взгляд, стоило бы поменять: не копию заводить, а **сказать один раз**.
Удаление оставить как есть — оно fail-closed и не оставляет нечитаемого пользовательского
текста на диске, — но убрать незаметность. Сейчас единственные данные, которые клавиатура
хранит о человеке, исчезают без следа, и он видит пустой список, не зная, сам ли он его
стёр. Канал для этого сообщения миссия уже построила, так что правка вышла бы маленькой.

Вариант «оставлять карантинную копию» я не рекомендую: до 128 КиБ пользовательского
текста лежали бы на диске неопределённо долго, ни один экран их не показывает и не даёт
удалить, а кода, умеющего эту копию прочитать, не существует.

Три варианта с плюсами и минусами — в `ask.json`, пункты `B2-a/b/c`.

### B3 — `forget` без `try/catch`, то есть падение процесса. Вынесена оператору

Не чинил по той же причине.

Одно наблюдение, которое стоит иметь в виду при ответе, и которое досье предлагало
проверить, а не принимать по умолчанию: **падение здесь ничего не спасает.** Обычный
аргумент «упасть громко лучше, чем тихо потерять данные» опирается на то, что данные
теряются. При неудачном `File.delete` слово **не** пропадает — оно просто остаётся
сохранённым. То есть цена падения — убитая клавиатура посреди набора в чужом приложении,
а выигрыша нет.

Заодно там мёртвая проверка: `deleteFile()` (`:377`) никогда не возвращает `false`, он
либо `true`, либо бросает, так что `if (deleteFile())` на `:141` не может быть ложным.

Рекомендация — `B3-b` в `ask.json`: ловить и отдавать отказ через канал, который теперь
существует. Правка на несколько строк именно потому, что A3 этот канал построил.

## Ловились ли находки существующими тестами

Нет, ни одна. До миссии личный словарь и пути вставки покрывали **21 файл тестов**
(6 в `dictionary/personal/`, 7 в `dictionary/personalstore/`, 2 в `settings/`,
плюс соседние в `suggestions/`), и прогон был зелёным при всех восьми дефектах на месте.

Три конкретных дыры, которые стоит назвать:

* **`dictionaryUnavailableListener` не упоминался ни в одном тесте.** Единственный канал
  обратной связи во всей подсистеме — и ноль тестов на то, кому и когда он срабатывает.
  `SuggestionsOfferControllerTest` покрывает только то, что происходит **после** вызова
  слушателя.
* **У класса «рапорт об успехе раньше результата» не было ни одного теста.** Ни стор, ни
  контроллер экрана не проверялись на то, *когда* становится известен исход мутации —
  проверялось только, что мутация в итоге происходит. С прямым (синхронным) исполнителем
  в тестах разница между «поставлено в очередь» и «записано» исчезает, и весь класс
  дефектов A2/A3/A5 оказался вне видимости харнесса. Тесты этой миссии обходят это,
  наблюдая опубликованный снимок **изнутри записи**, а не после неё.
* **`isConnected()` упоминался в одном тесте** (`BackspaceSelectionDesyncTest`, и то
  вскользь, в комментарии о том, что с null-соединением он просто `false`). На то, что
  пути вставки обязаны его спрашивать, тестов не было.

## Что пришлось тронуть в чужих тестах

Два места, оба вынужденные — правка меняет ровно ту строку исходника, которую тест
цитирует дословно. Смысл проверок сохранён, ни одна не ослаблена:

* `PersonalDictionaryErasureTest.erasingCoversEveryLanguageNotOnlyTheOneInView` —
  сигнатура `eraseAll` выросла на колбэк, а цикл теперь идёт по отфильтрованному списку.
  Проверка «идёт по всем, кого дали» усилена: теперь она пинает и то, что список
  получен из полного аргумента (`subtypeIds.filter`), и то, что цикл идёт по нему.
* `AutocorrectSourceContractTest` — **не тронут.** Он сломался на первой форме правки A4
  (второй `endBatchEdit()`), и вместо правки теста переписана форма охраны, чтобы
  замороженный контракт «один batch edit» остался дословно верным.

## Один дефект, который миссия сама себе сделала и починила

Стоит записать, потому что он тихий и мог уехать в релиз. Первая версия правки A2
выглядела так:

```kotlin
outcome?.onFinished(commitWrite(entries.upsert(word, normalized)))
```

В Kotlin `?.` короткозамыкает **всё выражение вместе с аргументом**. При `outcome == null`
— то есть на каждом вызове `addManually`, который не с экрана настроек, — `commitWrite`
не вызывался вообще, и добавление слова переставало работать полностью. Существующие
тесты этого не поймали: ни один не проверял `addManually` без колбэка после правки.
Нашлось при разборе того, почему новые тесты падают «не по той причине». Исправлено:
результат вычисляется отдельной строкой и только потом сообщается.
